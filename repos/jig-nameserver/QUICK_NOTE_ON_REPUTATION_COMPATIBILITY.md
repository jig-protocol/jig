Fundamentally, a decentralized communication system cannot have a centralized reputation system if that reputation system is tied into users' ability to communicate, servers' ability to serve, nameservers' ability to resolve, etc.

We think it's important enough to put reputation and the rulesets that define it and the proof-of-work that it influences into the primitives of this system, but if there is one central reputation system that Gigue defines, all this "high-sec" vs "null-sec" talk, or decentralization, or anonymity stuff: it's all show.

It won't be real, because we'll be setting global rules that define user speech, server behavior, nameserver behavior, etc. at a base level. We will have recreated Bluesky basically: a tool that _could have been_ decentralized, but instead is a centralized platform that pretends to be decentralized.

So: we need to decentralize reputation scoring as a primitive, _yet_ incentivize centralized reputation management for high-sec. Here's how:

1. Every nameserver maintains reputation scores for every user, server, and nameserver _it interacts with directly_. (no reason not to have a sparse matrix or to score thousands/millions/billions of entities you've never observed, right?)
2. That reputation is tied to the registry and feeds proof-of-work difficulty (and rate limits) for each entity. (particularly users, but we should think through implications for server <> server, nameserver <> nameserver, etc.)
3. Here's the trick: reputation is fundamentally tied to a _ruleset_: a code you upheld (or not) and a score of how well you did so over time. Each server or nameserver could potentially have their own - and in nullsec they probably do (or just don't bother linking up, even if the rules are ~roughly identical).
   a. But in high-sec, the nature of high-sec actually, is that there is a common ruleset (or a couple common ones) that _everyone_ uses. This is a broadband social contract and, if you are on the ruleset, you have a reputation score that is compatible cross-server, cross-nameserver, intelligible to everyone who is on the ruleset. Tribunals make sense in this world: they're using a code that everyone else knows, and they're judging you on a code you're expected to know. No surprises.
   b. There could be a couple competing systems here, I don't actually think that causes real problems, though it could potentially slow things down if it's _too_ fragmented at launch? I kinda expect Gigue to need to set the first high-sec ruleset and central nameserver and push heavily for a defacto standard high-sec island that most folks agglomerate to.
   c. Low-sec (or high-sec groups) would link up with _data contracts_: configs (toml, ideally) that explain how to translate rulesets and reputation scores from one system to the other and back. If I have a 30 on AcmeSrv and a -2 on BetaNet (making those numbers up, no idea if we want integers or whatever), there's no way to tell which is better _unless AcmeSrv and BetaNet have made an explicit agreement to say how their scores translate_.
   d. Presumably, this only works if the _rulesets_ are reasonably compatible. An example here would be Roblox and 4chan trying to set up a data contract across their servers: _super_ unlikely they'd find common ground about the rulesets they'd want their users to abide by, so their reputation numbers would be meaningless to each other.
   e. The implication would be that reputations come in key:value pairs and, if a server doesn't have a matching key, it treats the user as a new/unknown user. (You could presumably see servers wanting to _block based on the mere existence of a key_, like in the Roblox-4chan example... which we probably have to let them do, even thought the 4chan folks would create new accounts if they really wanted to join a Roblox server).
4. The elements we need to make this work are:
   a. **Users, servers, and nameservers all need to have a dict or map or set (or toml!) of ruleset keys and their associated reputation scores**, that they use when interacting with other entities.
   i. **It needs to be clear if servers and nameservers get scored on a ruleset by virtue of their aggregated members or by virtue of their own behavior.** There's no real reason why it couldn't be both - a ruleset would presumably be just a toml file that explains expectations for behaviors for interaction and penalties for failure. One ruleset audience could believe that it's meaningful to know what the aggregate reputation of each server they visit is, based on standard high-sec rules. Another could be more interested in how the server actually interacts with user PII and registration data and could care less about the behavior of the users on the server. Having tokenized rulesets allows for a lot of customization here.
   ii. **A symmetric system would insist that all entities could maintain one.** It would be an interesting challenge to implement, but a philosophically-curious one if e.g. users could implement a ruleset for servers they interact with and score them based on their behavior (or, similar to high-sec, maintain a broadband common set of expected behaviors for servers they frequent). It would go a long way towards ensuring power parity in the network.
   iii. It's a little unexpected to score nameservers - after all, the primary function is to register users, so there's not much reason to score them based on behavior. However, since they are the primary implementers of the rulesets, **there's good reason for them to score each other - and be scored by the other entities - based on the mesh between the rules they present and the rules they enforce, the interactions they have with servers and other nameservers, the way they handle tribunals and appeals, and in general the experience they create for the people they supervise / serve.** Again, creating an unscored class creates a power imbalance: there's probably not a good reason to start off that way.
   c. Rulesets - which we're presumably only identifying by a hash or uuid in the maps people are showing each other on entry - **need to be easily accessible throughout the system**. Hard, but not impossible: each entity should probably be responsible _at least_ for displaying their own, we should maintain a registry of common rulesets based on some sort of pareto distribution, and we can probably set some sort of incentive to share rulesets (especially e.g. based on the data contract linking system: implicit in the linking protocol is a mandatory provision that you host each other's rulesets).
   i. Importantly, **no entity should lose reputation from another without first seeing and acknowledging the ruleset they're participating with**. This is a _very_ important requirement for ensuring that reputation is a meaningful signal. (It's also going to be weird on busy servers, but I think we can solve that with a "you can't lose reputation from a ruleset you haven't seen" rule and some server rules on which rulesets are allowed to be used locally / which sets are globally applicable whenever you're logged on).
   d. **Score changes for each entity need to be visible to other entities** - both on the entity being measured and verified across others. (Nameservers are great for this, this is probably their primary function aside from initial identification and registry). Cross-referencing visible ledgers and changes across ledgers to maintain visibility in the system - without exposing too much information about individuals - is a good requirement for keeping high-sec in particular transparent and easy to navigate, and in particular difficult to fake a score change / hide an infraction.
   e. Each user, server, and nameserver should be able to **configure how they interact with other entities based on the ruleset + reputation combos they use**. (again, jig-config). This is easiest to imagine on the server side - "don't let in anyone with reputation < 0" - but users should also be able to throw warnings for risky users, avoid risky servers, stay away from hyperpunitive nameservers, etc.
   i. This is made _a little_ trickier by virtue of the fact that **the entity:ruleset ratio is not 1:1**, but in a toml file you just set multiple parameters and insist that any ruleset the entity is enforcing needs to be local (which also helps solve the hosting problem).
   f. And finally, each entity needs a way to **report** on another entity's behavior and **directly change their reputation score**.
   i. It's a decentralized system, so there's no "reputation police", even in high-sec (tribunals fire off of the initial violation being noticed and amplify it; they don't initiate on their own). If you do something that violates a ruleset in an interaction with me (that I observe? there's some UX / incredulity factor to think through here), I should get to push the penalty myself directly.
   ii. Maybe automatically? if I have AI hooked up to help with that, but that's certainly riskier.
   iii. If I do that and I'm wrong, that should be nameserver / tribunal appeal territory - and probably a reverse penalty on the incorrect applier, though that's presumably something expressly stated in the ruleset, to avoid frivolous penalization.
   iv. The process should be 1-on-1 at its heart, with the interaction -> penalty applied -> push into ledger, then other observers (in high-sec in particular) can decide if they are going to validate or invalidate the change and amplify or dampen or nullify the penalty applied.
   v. That then forms the core of the tribunal process: a quick snapshot occurring at penalty occurrence that provides enough information automatically to justify the ledger entry, and server / nameserver rules promoting bystander / server / tribunal amplification to quickly validate entries and in the event of bad behavior, rapidly penalize the bad actor such that they can't engage in the system effectively.
   vi. Note how _none_ of this requires manual intervention (beyond the initial _decision_ to apply the penalty), and _none_ of this requires central authority: Gigue / Jig Foundation / whoever didn't have to do anything. If we get the balance right, this can make the network, particularly in high-sec, self-healing on its own without centralized defenses and single-points-of-failure.
   vii. This can't replace basic safety / anti-stalking capabilities: block, report-to-real-life-police, etc. We have less-effective toolkit here than normal, but we can put it some basic tools (especially in-GUI) to help guide users to block abusive users and direct them to collect evidence they have local on their machine and report folks they know are dangerous to their local authorities to help keep them safe.

I think that's it. It's more complex than just # -> PoW, but it's more powerful and more useful. Fundamentally, the relationship is still the same: Servers and nameservers still take _their_ reputation scores when assigning PoW, it's just that they can modularly swap out the ruleset that informs those reputation scores, and those reputation scores can inform more than just PoW (or can inform PoW in different ways on different servers, as codified in jig-config).
