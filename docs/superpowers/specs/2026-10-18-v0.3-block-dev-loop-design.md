# v0.3 block developer loop and registry

**Date:** 2026-10-18
**Author:** DJ + Claude (lane Dv of the
[v0.2-close / M3-start plan](../plans/2026-10-18-v0.2-close-and-m3-start.md))
**Status:** Research pass. Recommendations only; nothing here is decided. No implementation code
exists. A plan with PR-sized slices follows DJ's approval.
**Builds on (decided, not re-opened here):** lane A's block ABI (#112, JEP-0006: decisions A1–A8),
lane C's capabilities, state and nesting (#117, JEP-0007: C1–C8), DJ's rule that every new signed
object is COSE_Sign1 over deterministic CBOR, and L3's removal of the old `jig block` surface
(#127). Reference guest: A's step 5, `text-block` as a `renderer` component (#158).

## Goal

The first half of the phase-2 exit criterion ([`ROADMAP.md`](../../ROADMAP.md)): *a third party
writes, signs and ships a block in under 10 minutes that runs identically on client and server.*
The roadmap's phase-2 list adds `jig block new/lint/sign/run`, block templates and a block registry
by CID. Product constraint 1 (the 60-second install, measured by `install-smoke.yml`) is the
on-ramp: the 10 minutes start where the 60 seconds end.

Lane A owns what a component is and what "identical" means. Lane C owns what a block may do.
This design owns how an author gets from nothing to a signed component that a server and a client
both run, how that component is named and found, and how CI proves the 10 minutes.

## Summary of recommendations

| # | Question | Recommendation |
| --- | --- | --- |
| Dv1 | Command surface | `new`, `build`, `lint`, `test`, `run`, `sign`, `verify`, `publish`. `build` embeds `wit-component` and the `jig-det-1` validator, so an author never installs `wasm-tools`. `run` and `test` call the same `jig-runtime` component path the server and client use; "identical" is proven by A's conformance vectors, not by sharing code. `publish` uploads to a server you name. |
| Dv2 | Templates | Rust only in v0.3, using `wit-bindgen` directly with no jig SDK crate. Three templates: `renderer` (first), `bot`, `composed` (each after the C slice it needs). TinyGo and JS cannot meet `jig-det-1` (runtime floats and WASI imports); that is a profile question for A, not a template question. |
| Dv3 | What is published | A new signed object, the **program manifest** (COSE_Sign1 over deterministic CBOR), plus the component bytes. Its CID is the **program CID**: what a message renders with, what an install names, what children pin and what operator policy allows. It carries no timestamp, so the same build always has the same CID. |
| Dv4 | Registry | No registry service. Every server is a CID-addressed store; a program is published by ingesting it (new kind `block-program`, stored, never executed on ingest) and fetched by CID from any server that holds it, verified by CID. Names arrive later through lane F's naming as author-signed pointers. Nameservers never hold bytes. |
| Dv5 | Trust | CID for integrity, author signature for origin, pin by CID with no automatic upgrades, operator policy (empty by default) for whether a server runs it. Clients need their own policy, which nothing yet defines (see Dv5's DJ question). Builds are not reproducible, so v0.3 trust in a program is trust in its author: the spec should say so. |
| Dv6 | KPI in CI | A new workflow, `block-dev-smoke.yml`, not a required check: on non-draft PRs that touch the loop, nightly on `main`, and after each release against the published install. A fresh runner with no Rust cache goes template → build → sign → publish → server `exec` receipt → client re-execution and comparison, with a 5-minute machine budget. |
| Dv7 | Order and docs | The local loop (`new`/`build`/`lint`/`run`) can start as soon as #127 and A's steps 3–4 merge; signing waits for A's COSE/CBOR crates (step 6); the end-to-end KPI waits for A's client comparison (step 7). The author's guide is written last against the CI script, so the two cannot drift. |

## Baseline (verified 2026-10-18 on `main` at `8792c5f`, plus the open A/C branches)

| Area | State |
| --- | --- |
| CLI | `jig block init` (templates for the removed `wasm32-wasi` target), `run` (ABI 2, WASI p1), and `lint`/`sign`/`verify`/`capabilities` stubs that print "not yet implemented". #127 deletes all but `run`. The CLI already embeds `jig-runtime` by default (feature `local-runtime`), so a CLI that executes components costs no new binary weight. |
| ABI | `jig:block@0.1.0` with worlds `renderer` and `bot` (#145). Validator for `jig-det-1` (#151). Canonical CBOR outcome hash (#148). `text-block` builds as a renderer component (#158). |
| Guest build | `text-block/build-artifact.sh`: `cargo build --target wasm32-unknown-unknown` with `RUSTFLAGS=-C link-arg=--max-memory=16777216`, then `wasm-tools component new`. CI installs `wasm-tools` with `cargo install`. |
| Reproducibility | Not reproducible. The same tree differs by about 1.4 KB between aarch64 macOS and x86_64 Linux under the same rustc (`build-artifact.sh` header), so CI checks artifacts by behaviour, not bytes. |
| Block identity | A block's CID hashes manifest, code and resources together (`jig-core/src/bundle.rs`). The manifest carries `hlc_ts` and `metadata`, so two deployments of the same code have different CIDs, and there is no separate code CID (C's baseline). |
| Distribution | `POST /api/v1/blocks` (ingest) and `GET /api/v1/blocks/{cid}` (behind the channel read gate). No program store, no names for code. |
| Trust rows | SC-01 (connector blocks: addressed by CID, author-signed, SHOULD be pinned) is "Accepted" only because no connector runs as a block. SC-02 covers jig's own release supply chain, not blocks. |
| CI | `ci.yml` required checks are `workspace`, `wasm-build` and `dependency-policy`; drafts and docs-only PRs skip the build jobs (the `changes` job); the schedule runs only `dependency-policy`. `install-smoke.yml` is a separate, path-filtered, non-required workflow, also called from `release.yml`. |

### Measurements for this design (scratch experiment, this container, not committed)

A minimal `renderer` in Rust (wit-bindgen 0.51, `format!` over integers and a string), built for
`wasm32-unknown-unknown` with `opt-level = "s"`, LTO, `panic = "abort"`:

| Step | Result |
| --- | --- |
| `rustup target add wasm32-unknown-unknown` | 3 s |
| Cold `cargo build --release` (empty target dir, crates downloaded) | 17.5 s wall, 40 s CPU |
| Core module | 19 KB, **0 float instructions, 0 imports** |
| Memory | `(memory 17)`: **no declared maximum**, which `jig-det-1` refuses. A template must set `--max-memory`. |
| `wasm-tools component new` | 20.5 KB component; imports only `jig:block/types@0.1.0`, exports `jig:block/render@0.1.0` |
| `cargo install wasm-tools --locked` | **2 min 23 s** wall, 8 min CPU, on this multi-core container. On a 4-vCPU CI runner, expect 4–6 minutes. |

Two conclusions follow. The Rust path fits easily in 10 minutes. Installing `wasm-tools` alone
would eat half of it, so the loop must not depend on it.

## Q1. Command surface (Dv1)

### The commands

| Command | Does | Implementation it reuses |
| --- | --- | --- |
| `jig block new <name> [--template renderer\|bot\|composed]` | Writes a project: `Cargo.toml`, `src/lib.rs`, `.cargo/config.toml`, `jig-block.toml`, `wit/` (the `jig:block` package copied out of the `jig` binary, so the WIT always matches what this `jig` links), `tests/vectors/`. Prints the next three commands. | WIT embedded from `repos/jig-spec/wit/` at build time |
| `jig block build` | Runs the template's build command (for Rust, `cargo build --release --target wasm32-unknown-unknown`), wraps the core module with `wit-component`'s `ComponentEncoder` **in-process**, then runs `lint`. Writes `target/jig/<name>.wasm` and prints the component's hash. | `wit-component` (already in the lockfile at 0.258.3, matching wasmtime 49), jig-core's validator (#151) |
| `jig block lint [path]` | `jig-det-1` on the component, plus manifest checks: the requested capabilities are known names with valid scopes (C1), the world matches the exports, children are listed with CIDs. Errors are written for authors: a float instruction is reported with the function it is in (from the name section) and the usual cause ("`serde_json` or float formatting"). | The same validator the server runs at upload; no second copy |
| `jig block test` | Runs every vector in `tests/vectors/` through `jig-runtime` and compares outcome class and hash. `--bless` records new expected hashes. | A's component path (step 4) and outcome hash (step 2) |
| `jig block run [--input …] [--sender … --channel … --seq …]` | Executes once with a synthesized `invocation` and prints the outcome (`ok`/`error`/`incomplete`), the outcome hash and the decoded output. `--replay <message-cid> --server <url>` fetches a real message and the server's `exec` receipt, re-executes, and reports agree or diverge. | The same `jig-runtime` function the server and client call |
| `jig block sign` | Builds the program manifest (Dv3) from `jig-block.toml`, signs it as COSE_Sign1 with the author's DID key from `jig init`, and writes `target/jig/<name>.jigprog` (manifest plus component). Prints the program CID. | A's COSE_Sign1 signer (step 6) |
| `jig block verify <file\|cid> [--server <url>]` | Checks the CID over the bytes, the author signature, `jig-det-1`, that every declared child is present and itself verifies, and the embedded vectors. Exactly the checks a server's ingest runs on a `block-program` (one implementation in jig-core). | |
| `jig block publish [--server <url>] [--channel <id>]` | Uploads the `.jigprog` to a server through `ingest` (Dv4). Prints the program CID and the server's receipt. Idempotent: re-publishing the same CID is a no-op. | Existing `POST /api/v1/blocks` |

`run` stays the name for one execution and `test` for the vector suite. Folding `test` into `run
--vectors` is an equally good option; it saves a command and costs discoverability.

`jig block capabilities` goes for good. `lint` prints what a program requests, and an install
(C's `block-install`) is where authority is granted; a separate command would describe neither.

### Is publishing done by posting to a server?

| Option | How | For | Against |
| --- | --- | --- | --- |
| **A. Upload to a server you name, through `ingest` (recommended)** | `publish` sends a `block-program` block. The server validates it and stores it by CID. It does not execute it (A7: execution is policy, not upload). | Reuses ingest's gates (signature, admission, rate limits, kind allowlist) and the existing CID fetch. The program gets an `ingest` record, so its publication is ordered and timestamped by a server. | Each server you want to use needs a copy until F's cross-server fetch exists. |
| B. No publish; programs travel as files | The author hands out the `.jigprog`; an install or a message carries the bytes inline. | No new server surface. | A 20–200 KB component inside every message that uses it. No catalogue. |
| C. Publish to an external registry (OCI, or the Bytecode Alliance's `wkg`/warg) | `publish` pushes there; servers pull. | Existing tooling, mirrors. | A second trust root and a network dependency in every server, which "runs on a potato" argues against. OCI digests are SHA-256, not jig's BLAKE3 CIDs, so every reference needs a mapping. |

**Recommendation: A.** Keep B possible: `verify` and `install` accept a local file, so a program
can move without any server holding it first.

### How `run` matches server execution

- **One function.** `jig block run`, the server's executor and `jig-client` all call A's single
  component path in `jig-runtime` (A4). The CLI builds the engine with A's explicit profile
  (`concurrency_support(false)`, NaN canonicalization, fuel, epoch for liveness only), never
  wasmtime defaults.
- **Same code is not the proof.** A different wasmtime patch, architecture or Pulley can still
  diverge. The proof is A's conformance vectors (step 8) on x86_64 and aarch64, native and Pulley.
  `run` prints the engine version and profile so a divergence report names both.
- **Same inputs.** A local run synthesizes the `invocation` (default sender is the author's DID,
  channel a fixed test CID, `seq` 0, HLC 0). Only `--replay` uses a real `ingest` record, and
  only `--replay` claims anything about a real message.
- **Same outcome classes.** Fuel, stack or epoch exhaustion prints `incomplete` with the reason
  and no hash, and `--replay` never reports `incomplete` as a divergence (A3).
- **Local runs sign nothing.** A receipt signed by the author about their own program asserts
  nothing a verifier can use. The author's evidence is the vectors (Dv3's `examples`), which any
  host can re-run.

## Q2. Templates (Dv2)

### Which languages

| Option | Fits `jig-det-1` today? | For | Against |
| --- | --- | --- | --- |
| **A. Rust only, wit-bindgen directly (recommended)** | Yes, measured above: zero imports, zero floats for ordinary code. | Same toolchain as jig and as `text-block`; one template set to keep correct; `wasm32-unknown-unknown` is tier 2 and already in `rust-toolchain.toml`. | One language. |
| B. Rust plus TinyGo | Not expected to (unverified). TinyGo's component path goes through `wasm32-wasip2` and `wit-bindgen-go`, which imports WASI, and its runtime and `fmt` carry float code that the float ban refuses even when unreachable. | Go reach. | Probably cannot pass the validator at all. A spike would settle it, but a fix would mean a TinyGo target built for jig. |
| C. Rust plus JS (`componentize-js`) | No. It embeds SpiderMonkey (StarlingMonkey), which is full of floats and imports WASI. | The largest author base. | Needs a determinism profile that admits floats with NaN canonicalization and virtualised WASI: a `jig-det-2`, which A deferred deliberately, and jco cannot canonicalize NaNs. |
| D. Rust plus C (`wit-bindgen c`, freestanding clang) | Plausibly, with `-ffreestanding` and no libm. Unverified. | No runtime, so it is easy to keep inside the profile. | Small audience; memory safety is the author's problem. |

**Recommendation: A for v0.3.** Say plainly in the guide that other languages wait on the profile,
and why. If DJ wants a second language for reach, D is the one that can work under `jig-det-1`;
Go and JS are an A-lane question (a `jig-det-2` with floats), not a template.

### No jig SDK crate in v0.3

| Option | For | Against |
| --- | --- | --- |
| **A. Templates depend on `wit-bindgen` only; `new` copies the WIT in (recommended)** | Nothing new on crates.io, so no new SC-02 surface and no crate to keep in step with the WIT. The generated code is plain and visible. | Some boilerplate in each template (`generate!`, `export!`). |
| B. A `jig-block` crate with the WIT inside and helper types (payload builders, a test harness) | Shorter templates; a native test harness. | A crates.io publication with its own release, signing and yanking process; a second place the WIT lives. |

**Recommendation: A** until `jig:block` reaches 1.0.0 at the v0.3 exit, then revisit. The
template pins `wit-bindgen` to the exact version `jig` is tested with, and `lint` warns when the
project's lockfile differs.

### What each template demonstrates

| Template | Shows | Available after |
| --- | --- | --- |
| `renderer` | A pure render: reads `invocation.input` (text), returns `text/plain` or a small structured payload. Native `cargo test` of the pure function, plus two vectors. This is the KPI template. | #127, A steps 3–4 |
| `bot` | State and effects: a counter bot that keeps a count in its state blob and returns a `post` effect on a command prefix. Its `jig-block.toml` requests `effects.post` and `effects.state` with tight scopes, and the guide shows the owner's `block-install` that grants them. | C slices 3–5 |
| `composed` | A renderer that pins one child renderer by CID, offers it nothing, and branches on the child's deterministic `failed`. The exit criterion's second half, by example. | C slice 8 |

### How a template stays inside `jig-det-1`

Each item is a way a correct-looking project fails the validator. The template sets it, and
`lint` explains it when someone undoes it.

| Hazard | Template does | `lint` says |
| --- | --- | --- |
| WASI imports (`wasm32-wasip1`/`wasip2`, or std's print and panic machinery) | `.cargo/config.toml` sets `build.target = "wasm32-unknown-unknown"` | Names the `wasi:*` import and the target to use |
| No memory maximum (the measured default) | `rustflags = ["-C", "link-arg=--max-memory=…"]`, sized from `jig-block.toml`'s memory limit | `MemoryMissingMaximum`, with the flag |
| Floats (`serde_json`, `{:.2}`, `as f64`, most of `std::fmt` for floats) | Templates use `postcard` or hand-written encoding, no floats | The function containing the float instruction and the likely crate |
| Non-portable stack exhaustion (A's risk) | A conservative stack, set with `-C link-arg=-zstack-size=…` | Warns when the stack is above the template default |
| Panics | `panic = "abort"`: a panic is `unreachable`, a deterministic `error` outcome | Nothing: it is allowed |
| Size | `opt-level = "s"`, LTO, `strip` | Warns above a size threshold (the host's compile cost is unmetered; C's AB-07) |
| Component-model async, threads | Not reachable from the template | Refused by the validator |

## Q3. What is published, and the registry by CID (Dv3, Dv4)

### The thing a registry holds: the program

C's baseline names the problem: a block's CID covers manifest, code and a timestamp together, so
"the CID of this bot" changes on every deployment, and A7's policy "by component CID" names only
the bytes, not what the code asks for. A registry needs one stable identity that pins code,
requested authority and children together.

**Recommendation: a new signed object, the program manifest.** Deterministic CBOR, signed as
COSE_Sign1 (DJ's rule for new signed objects), with these fields:

| Field | Meaning |
| --- | --- |
| `author` | The author's `did:jig`. The COSE `kid`. |
| `name`, `version` | Display name and semver. Lineage only; never resolved to a CID automatically. |
| `world` | `jig:block/renderer@0.1.0` or `jig:block/bot@0.1.0` (A6). |
| `component` | BLAKE3 hash of the component bytes (A's receipt field `component`). |
| `requests` | C1 capability names with typed scopes: the ceiling an install may grant. |
| `children`, `offers` | C5's pinned child **program** CIDs and per-child offers. |
| `limits` | Memory maximum and fuel ceiling the author tested with. |
| `examples` | Vectors: invocation, expected outcome class and hash. |
| `supersedes` | Optional earlier program CID by the same author, for "a newer version exists". |
| `source` | Optional, unverified claim: repository, commit, `Cargo.lock` hash, rustc version. |

It has **no timestamp**. When it was published is the `ingest` record's job. The same manifest and
component therefore always give the same CID, so republishing is idempotent and two people who
build and sign the same thing agree on its name.

**The program CID** is BLAKE3 over the labelled parts `manifest` (the manifest's deterministic
CBOR, unsigned) and `code` (the component), using `bundle.rs`'s existing derivation. The signature
is not inside the CID:

| Option | For | Against |
| --- | --- | --- |
| **A. CID over the unsigned manifest and code; the author's COSE_Sign1 travels beside it (recommended)** | The identity is a fact about content. The manifest names the author, so nobody else can claim the CID, and a forged signature never verifies. Later signatures over the same CID (an audit, a reproducible-build claim, an operator's allowlist entry, R's reports) attach to one stable name. | A program without its signature is unauthenticated, so every store keeps the two together. |
| B. CID over the COSE_Sign1 bytes and the code | One blob; the signature can never be lost. | Every attestation needs a second name for the same program. |

**What uses the program CID:**
- an install: C's `block-install.block` names a program CID;
- a child: C's `children: [cid…]` are program CIDs, so the parent's CID pins the whole tree,
  requests included, which is what C's "policy covers the closure" needs;
- operator policy: A7 allows by program CID or by author. Allowing by component hash alone would
  approve the code under any manifest, including one that requests more;
- a message that renders with a third-party renderer: the message names the program CID and
  carries the input. The field's exact shape belongs in the block-manifest change with A and C
  (A left "the manifest field that names a block's component and world" to Dv and C). Proposal:
  a new kind `render` with `program: <cid>` and the input payload. The server executes it only if
  policy allows (an `exec` receipt), and otherwise accepts it (`accepted`) and leaves execution to
  clients (A7).
- receipts: `exec` keeps A's `component` and adds `program`.

### Where it lives: three options

| Option | Shape | For | Against |
| --- | --- | --- | --- |
| **A. Every server is a CID store; publish is ingest; fetch by CID from any holder (recommended)** | `block-program` is a block kind that the pipeline validates (`verify`'s checks), stores and gives an `accepted` receipt, and never executes on ingest. `GET /api/v1/blocks/{cid}` serves it, behind the read gate of the channel it was published into. Authors publish into an open channel they control (their own feed, or a community catalogue channel), which also makes a channel a catalogue. | No new service. Integrity is the CID, so it does not matter which server serves the bytes. The `ingest` record (`seq`, `prev`, `ingest_hlc`) gives each publication a server-signed, ordered entry: a weak transparency log at no cost. Federation carries it as a block kind once F's contract lists it. | Discovery is only as good as the channels people make. No global search. |
| B. A per-server registry endpoint outside ingest (`/api/v1/programs`) | A program store with its own upload route and index. | A clean listing API. | A second write path, against the "one write path" principle, plus its own auth and rate limits. |
| C. Nameserver-advertised | Nameservers map names to program CIDs, or hold the bytes. | Global names. | Nameservers are being cut down to naming (L6); holding bytes makes them a CDN with a different trust model. Names for programs are F's problem and should reuse F's machinery, not a parallel one. |

**Recommendation: A, and names through F later.** When F's verified names land, a program name is an
author-signed pointer (`name → program CID`, with a sequence number), resolved and pinned the same
way F pins handles. Resolving a name never upgrades an existing install or a rendered message;
it only helps a person find a CID to choose.

**Cross-server fetch.** In v0.3 a server executes or serves only programs it holds. A client
fetches from its own server. Pulling a missing program from another server by CID, verified by
CID, is a term of F's channel contract ("the block kinds the server relays"), not a Dv design.

### Discovery, pinning and trust (SC-01, SC-02)

What each mechanism establishes, and what it does not:

| Mechanism | Establishes | Does not establish |
| --- | --- | --- |
| CID | These bytes are the program everyone else means. A malicious mirror cannot substitute code. | That the program is any good. |
| Author COSE signature | Which DID published it. Key compromise is the author's problem, as for any DID. | Who wrote the source, or what went into the build. |
| Pinning by CID | An install, a child and a message each name one exact program. A compromised author key cannot change what is already pinned. | Protection for someone who installs the attacker's new CID. |
| Operator policy (C2, A7; empty by default) | Whether this server executes it at all. Allowing a parent by CID allows exactly its tree; allowing by author never extends to children by other authors (C). | Anything on clients. |
| `jig-det-1` and the sandbox | Bounded, deterministic execution with no ambient authority. | Safety against a wasmtime zero-day (SC-03). |
| `examples` vectors | Executors agree on the author's own cases, so a divergence shows up at install, not in a channel. | That the program does what its name says; the author picks the vectors. |
| `source` claim | Where to look. | That this source built these bytes: builds are not reproducible (baseline). |

The weak link is the build. Because components are not reproducible across hosts, nobody can
check a program against its source. So in v0.3, **trusting a program means trusting its author.**
The spec and the guide should say exactly that. Reproducible builds (a pinned toolchain image,
compared by bytes) would turn the `source` claim into something checkable, as v0.4 work.

**Upgrades and revocation.**
- No automatic upgrades anywhere. A new version is a new CID. A bot moves to it by a new
  `block-install` with C's `inherits_state_from`, signed by the owner.
- An author may publish a signed `program-yank` naming a CID and a reason. It is advisory: pinned
  uses keep working, clients show a warning, and an operator's policy may treat it as a removal.
- Reports and deny-lists of program CIDs or authors are lane R's (JEP-0010). This design only
  requires that a program CID and an author DID be what those lists name.

**Threat register (edits go in the implementation PRs).**
- **SC-01** widens from "connector or bridge blocks" to every third-party program. Mitigation:
  pinned by program CID, author-signed, executed by a server only under operator policy, bounded
  by `jig-det-1`; no automatic upgrade. Status: Partial once `block-program` ingest lands.
- **SC-02** gains a block-toolchain clause: templates pin `wit-bindgen`; the WIT comes from the
  `jig` binary, not the network; `build` needs no tool beyond `cargo` and `jig`. Builds are not
  reproducible, and the row says so.
- **AB-07** (C's bot amplification) gains client-side compile amplification (see Dv5's DJ
  question).

### A gap: client execution policy (DJ question)

C2 and A7 define operator policy for servers. Nothing defines what a **client** runs, and the
exit criterion needs clients to run third-party renderers: in encrypted channels (C6) only members
run anything.

| Option | For | Against |
| --- | --- | --- |
| **A. Clients run any renderer a displayed message names, inside `jig-det-1`, with a per-user deny list and a cap on distinct uncached programs compiled per channel per minute; past the cap, show fallback text and a "run" button (recommended)** | Third-party blocks actually render, which the KPI needs. A renderer has no authority (no imports beyond `compose` over pinned children), so the exposure is CPU and a sandbox escape. The cap answers compile amplification: compiling costs about 16 ms per component, unmetered (C's AB-07), so 1,000 distinct CIDs would cost a client about 16 s. | Every user's device runs strangers' code by default. A wasmtime zero-day reaches clients, not just servers. |
| B. Run only renderers by authors who are members of the channel, or contacts | A smaller exposure. | In an open channel anyone can be a member; the rule mostly adds friction. |
| C. Click to run, always | The smallest exposure. | Third-party blocks become a curiosity, and the exit criterion's "runs on client" is met only by people who click. |

## Q4. The 10-minute KPI as a CI job (Dv6)

### What CI can measure

The criterion is a person's ten minutes. CI can measure the machine's share and prove that the
documented steps work from nothing. It cannot measure the human's share. So:
- CI enforces a **machine budget of 5 minutes**, half the criterion, leaving the other half for
  reading the guide and editing one function.
- Each release, someone who has not seen the loop follows the guide with a stopwatch and records
  the time in the release notes. That is the honest measure of the criterion, and it is cheap.

### The job

A fresh `ubuntu-24.04` runner, **with no Rust cache** (a cache would hide the cold build that
every new author pays for), runs `scripts/block-dev-smoke.sh <budget-seconds>`:

1. Start the clock. Install the `jig` under test (as `install-smoke` does: a local mirror of the
   PR's build on PRs, the published release otherwise). Start a local `jig-server` whose operator
   policy allows the test author's DID.
2. `rustup` minimal profile plus `wasm32-unknown-unknown`, if absent (counted: a third party may
   not have Rust).
3. `jig init`, `jig block new hello --template renderer`, then a scripted one-line edit, so the
   build is not of untouched template code.
4. `jig block build`, `jig block test`, `jig block sign`.
5. `jig block publish --server … --channel <open channel>`.
6. Post a `render` message that names the program; wait for the server's `exec` receipt.
7. `jig block run --replay <message> --server …`, which is the client's re-execution through
   `jig-client` (A's step 7): it must report agreement on the outcome hash.
8. Stop the clock. Fail when over budget; print each step's time either way.

The PR's `jig` build happens before the clock starts, as in `install-smoke`'s PR job, since an
author installs a release, not a build.

### How it fits the existing gating

| Constraint | How the job meets it |
| --- | --- |
| Required checks must not be renamed | A new workflow, `block-dev-smoke.yml`. Nothing in `ci.yml` changes, and it is not made required. It can be promoted to required once it has been stable for a few weeks; that is DJ's call. |
| Drafts and docs-only PRs skip builds | `pull_request` with `types: [opened, synchronize, reopened, ready_for_review]`, `if: !draft`, and a `paths:` filter (the CLI's `block` commands, `templates/`, `jig-runtime`, the jig-core validator, `jig-spec/wit/`, the `jig-pipeline` program ingest, `Cargo.lock`, the script and the workflow). Docs-only PRs never match. |
| Nightly | Its own `schedule` on `main` (off the hour, as `ci.yml` does), Linux and macOS. It catches what a pinned workflow cannot: a new `wit-bindgen` on crates.io, a rustup change, network drift. GitHub disables schedules after 60 days without activity, as `ci.yml` already notes. |
| Release | `workflow_call` from `release.yml` after publish, like `install-smoke`, against the published install on Linux and macOS. The workflow belongs to lane L5. |
| Merge queue | Not in `merge_group`: the queue runs only required checks, and a network-dependent five-minute job would slow every merge. |

### The author's guide

One page, written against `scripts/block-dev-smoke.sh` so that the guide and the script are the
same steps. Contents: install, `new`, the one function to edit, `build`/`test`/`run`, `sign`,
`publish`, posting a message that uses it, and seeing the client agree with the server. Then a
page per template (`bot`: what an install grants; `composed`: what an offer withholds). A
"why it was refused" page maps every `lint` error to its cause. The guide's location is L1's to

## Risks and unknowns

- **wit-bindgen drift.** A new wit-bindgen can change the core module's shape. The nightly run
  catches it; the template's exact pin keeps authors on the tested version.
- **Cold-build time on a 2-core laptop** may be several times the 17.5 s measured here. That still
  fits, but the budget should be measured on the CI runner before it is fixed.
- **Float leaks from dependencies** are the most likely author failure. `lint`'s message is the
  mitigation. If authors keep hitting it, a `#![no_std]` template option is the fallback.
- **TinyGo and C** were not built in this pass. The table states expectations; a half-day spike
  would replace them with facts if DJ wants a second language.
- **Binary size.** `wit-component` adds to `jig`, which the 60-second install downloads. The CLI
  already embeds `jig-runtime`, so the increase should be small; measure it in slice 1.
