# v0.0.3-alpha.email (in-process email bridge) Design

**Date:** 2026-05-25
**Author:** DJ + Claude
**Status:** Approved
**Builds on:** [v0.0.3-alpha.1 chore](2026-05-21-v0.0.3-alpha.1-chore-design.md) — specifically alpha.1a's `jig-bridge-core` (`Bridge` trait + `BridgeRegistry` + `[bridges]`/`[bridge.<name>]` policy).

## Goal

Migrate `jig-bridge-email` from a standalone external SMTP daemon (that HTTP-POSTs to `jig-server`) into an **in-process `Bridge` implementation** loaded by `jig-server` via the alpha.1a `BridgeRegistry`. This is the first real consumer of `jig-bridge-core` and will surface the trait/context extensions every future bridge needs. Ships all three routing prongs in **restricted-mode** (1:1 conversations).

Out of scope (deferred to alpha.email.2 / "open-mode"): multiparty email-thread → group-channel resolution; shadow-DIDs acting as fuller participants; raw-SMTP inbound/outbound; IMAP/POP3 adapters.

## Routing prongs (all three, restricted-mode)

1. **Jig → Jig (discovery):** when resolving an email address that is *actually* a registered Jig alias, use the real DID as a native channel member — no email sent. Resolution via nameserver, cached in a local address book.
2. **Jig → Email (outbound):** a real Jig user posts a block to a channel containing a bridge-managed shadow DID → the bridge translates and sends email via the provider.
3. **Email → Jig (inbound):** provider receives mail → webhook → bridge converts to a `text-render` block submitted as the sender's shadow DID.

## Locked decisions (carried from v0.0.2 brainstorm)

- **Resend** is the default provider, behind a **pluggable `EmailProvider` trait**.
- **Inline-only, 25 MB attachment cap**, documented limit (no object-storage offload in alpha.email).
- **Pass-through encryption:** the bridge never decrypts E2EE traffic and never holds *real users'* private keys. It *does* hold its own **proxy/shadow** identities (see below) — these are the bridge's own identities, not users' keys, so this is consistent with "bridges never hold private keys."

## Architecture

`jig-bridge-email` becomes a **library-only** crate exposing `EmailBridge: Bridge`, loaded in-process by `jig-server`. The standalone binary and raw-SMTP modules are retired.

```
                          jig-server (axum app, one port)
   ┌──────────────────────────────────────────────────────────────┐
   │  /_bridge/email/inbound  ◄── provider webhook (Resend POSTs)   │
   │         │                  (route mounted via                  │
   │         ▼                   BridgeContext.mount_router)         │
   │   EmailBridge::webhook_handler                                 │
   │         │ verify → parse → dedup → resolve sender/recipient    │
   │         │ (address book) → build text-render block             │
   │         ▼                                                       │
   │   ctx.submit(block as shadow-DID)  ──► jig-pipeline::ingest    │
   │                                              │                  │
   │                                              ▼                  │
   │                                          Fanout.broadcast       │
   │                          ┌───────────────────┼─────────────┐   │
   │                       WSS subs          federation     bridge   │
   │                                                         sink    │
   │                                          (managed-DID match)    │
   │                                                  │              │
   │                                                  ▼              │
   │                                    EmailBridge::outbound(block) │
   │                                          │ dedup → translate    │
   │                                          ▼                      │
   │                                    Provider::send (Resend)  ──► email
   └──────────────────────────────────────────────────────────────┘
```

### `jig-bridge-core` extensions (v0.0.3 bump — all additive)

The alpha.1a `Bridge` trait signature (`name`/`start`/`outbound`/`shutdown`) is **unchanged**. Only `BridgeContext` grows, with three new handles:

1. **`mount_router`** — lets `start()` register an axum sub-router that jig-server merges under `/_bridge/<name>/`. Exposes the inbound webhook on the single server port (potato-friendly; uniform namespace for all future HTTP bridges). Adds an `axum` dependency to `jig-bridge-core`, **gated behind a `web` feature** so non-HTTP bridges (e.g. a future IRC bridge) don't pay for it.

2. **`register_managed_did(did)`** — registers a DID as owned by this bridge. The fanout layer gains a **bridge sink**: on `broadcast`, for each channel member that is a registered managed DID, it invokes the owning bridge's `outbound(block)`. The bridge calls this at `start()` (for address-book entries it already holds) and whenever it mints a new shadow DID. This is what makes the **server-driven `outbound()`** model work.

3. **`storage: Arc<dyn BridgeStorage>`** — the bridge's canonical persistence handle. See Storage below.

### Server-driven outbound trigger

The server (not the bridge) decides *when* to emit: the fanout bridge-sink matches delivered-block channel members against the managed-DID registry and calls `bridge.outbound(block)`. The bridge owns only the *how* (translate + send). `ctx.subscribe` is unused for email — no duplicated membership/fanout state in the bridge. This matches the `Bridge` trait's documented lifecycle (step 4).

## Components (`repos/bridges/email/src/`)

Library-only. **Retire**: `main.rs` (binary), `router_old.rs`, `smtp_client.rs`, `smtp_server.rs`, and the bridge-owned SQLite store in `storage.rs`.

- **`lib.rs`** — exports `EmailBridge` + `EmailBridgeConfig`.
- **`bridge.rs`** — `EmailBridge`: holds config, provider, address book, managed-DID keystore. Implements `start`/`outbound`/`shutdown`.
- **`provider.rs`** — `EmailProvider` trait + `ResendProvider` (default impl). The pluggable seam.
- **`address_book.rs`** — email↔DID resolution cache over `BridgeStorage` (nameserver-backed, TTL, expire-on-failure).
- **`identity.rs`** — shadow-DID derivation (KDF) + managed-DID registration.
- **`inbound.rs`** — webhook axum handler: verify → parse → dedup → block → `ctx.submit`.
- **`outbound.rs`** — block → email translation (reuses `formatter`).
- **`formatter.rs`, `parser.rs`, `types.rs`** — kept, trimmed to inbound/outbound needs.

### `EmailProvider` trait (Resend default, pluggable)

```rust
#[async_trait]
pub trait EmailProvider: Send + Sync {
    /// Outbound: send a translated email. Returns the provider's message id.
    async fn send(&self, msg: &OutboundEmail) -> Result<ProviderMessageId>;
    /// Inbound: parse this provider's webhook payload into a normalized email.
    /// Returns None for non-deliverable events (bounce / delivery-status) that
    /// the bridge logs but does not forward.
    fn parse_webhook(&self, headers: &HeaderMap, body: &[u8]) -> Result<Option<InboundEmail>>;
    /// Verify the webhook signature (Resend signs with a shared secret).
    fn verify_webhook(&self, headers: &HeaderMap, body: &[u8]) -> Result<()>;
}
```

### Shadow-DID derivation (`identity.rs`)

`seed = HKDF(bridge_secret, "jig-bridge-email-shadow:" + normalized_email)` → ed25519 keypair → DID. **Deterministic** across restarts (no key persistence; a restart reconstructs identical DIDs). The bridge legitimately owns these proxy identities — they are the bridge's *own* email-side representation of a participant, never a real user's Jig key. `bridge_secret` comes from `[bridge.email.config]`. Email normalization: lowercase + trim; optional `+tag` stripping (config flag).

### Address book (`address_book.rs`)

`resolve(email) -> Resolution`:
- Check `storage` cache (ns `"addrbook"`, key = normalized email); if within TTL, return it.
- Else call nameserver `/v1/resolve/<email-as-alias>`. Hit → `Resolution::NativeJig(real_did)`. Miss → `Resolution::EmailShadow(shadow_did)` (derive + `register_managed_did`).
- Cache with default TTL (config; e.g. 3600s). On outbound native-route delivery failure, **expire the entry** so the next resolve re-pulls from the nameserver (handles an email user who later registers a real DID, or vice versa).

### Storage — `BridgeStorage` (canonical, server-owned)

The bridge does **not** open its own database. It rides the server's canonical storage backend so it automatically follows the server's storage tier (SQLite now; Postgres/CockroachDB later per the alpha.1 `repos/storage/` forward-state).

`jig-bridge-core` defines a minimal, backend-agnostic trait:

```rust
#[async_trait]
pub trait BridgeStorage: Send + Sync {
    async fn put(&self, ns: &str, key: &str, value: &[u8], expires_at: Option<i64>) -> Result<()>;
    async fn get(&self, ns: &str, key: &str) -> Result<Option<Vec<u8>>>;  // None if absent OR expired
    async fn delete(&self, ns: &str, key: &str) -> Result<()>;
    async fn sweep_expired(&self, ns: &str) -> Result<u64>;
}
```

- `BridgeContext` carries `storage: Arc<dyn BridgeStorage>`.
- **jig-server implements it once** over its canonical store — today a single `bridge_kv(bridge_name, ns, key, value BLOB, expires_at)` table in the same SQLite the pipeline uses (same connection/pool, **no second file**). When the storage tier migrates, this impl moves with it and the bridge inherits it for free.
- The EmailBridge uses it for the address book (ns `"addrbook"`) and idempotency (ns `"inbound-seen"`, `"outbound-seen"`).

**Limitation flag:** only the SQLite `BridgeStorage` impl ships in v0.0.3 — the abstraction is unproven against Postgres/Cockroach. Surface `naively_single_backend_bridge_storage` in `jig-server`'s `unsafe_options_active()` whenever any bridge is loaded. Loud acknowledgement (per the antipattern naming convention) that the seam exists with one backend.

## Data flow

### Inbound (Email → Jig)

1. Provider receives mail for the configured domain → POSTs `/_bridge/email/inbound`.
2. Handler: `provider.verify_webhook()` (bad sig → `401`). Then `provider.parse_webhook()` → `Option<InboundEmail>` (None → `200`, logged, no forward).
3. **Dedup:** key = provider message-id. If `storage.get("inbound-seen", msg_id)` present → `200`, skip (provider redelivery).
4. Resolve **sender** → address book → `EmailShadow(shadow_did)` (mint + `register_managed_did` if new). Shadow DID is the block author.
5. Resolve **recipient** through the same address-book path → `NativeJig(real_did)` (the Jig user being emailed) → derive the target channel from the `(shadow_did, real_did)` pair (see Channel resolution).
6. Build a `text-render` block (subject+body via formatter/parser), signed by the shadow DID's derived key, `hlc = now`.
7. `ctx.submit(block)` → ingest. The bridge-signed block passes sig verification; TOFU binds email→shadow_did. On `SubmitDenied` → translate to a provider failure (never silently drop): `RateLimited` → `429`; `PolicyBlocked`/`Unavailable` → `5xx`.
8. `storage.put("inbound-seen", msg_id, …, ttl)`.

### Outbound (Jig → Email)

1. Real Jig user posts a `text-render` block to a channel that includes a shadow DID.
2. Ingest → `Fanout.broadcast` → bridge sink matches the managed DID → `EmailBridge::outbound(block)`.
3. **Dedup:** key = `delivery_cid`. If seen → skip (fanout double-fire / restart).
4. Decode block → reverse-resolve the shadow-DID member → recipient `email` (the `to`); render subject/body (+ optional viral footer per config).
5. `provider.send(OutboundEmail{ to, from, … })` where **`from` = `<sender-local-part>@<bridge-domain>`**: `sender-local-part` is the real Jig author's nameserver alias if it has one, else a stable synthesized local-part derived from the author DID's short form. This gives the email recipient a reply-to that routes back inbound to the correct sender. `bridge-domain` comes from `[bridge.email.config]`.
6. Success → `storage.put("outbound-seen", delivery_cid, …, ttl)`. Failure → bounded in-memory retry (3 attempts, backoff); after exhaustion, drop + error log/metric. No persistent outbound queue (the retired daemon's model) — fanout already delivered the block to native members.

### Channel resolution (restricted-mode, 1:1 only)

The target channel for an inbound email is derived deterministically from the participant pair: a 2-party email↔Jig conversation maps to a restricted-membership channel slug like `#dm/<sorted-did-pair-hash>` (consistent with "DMs are restricted-membership channels"). The bridge creates the channel + adds both members (real DID + shadow DID) on first contact if absent. **Multiparty/group threads are deferred to alpha.email.2 ("open-mode").**

## Error handling

- Webhook bad signature → `401`; malformed → `400`; bounce/status event → `200` + log, no forward.
- `ctx.submit` → `SubmitDenied` → provider-appropriate failure (`429`/`5xx`), never silent drop.
- Outbound provider failure → bounded retry (3×, backoff) → drop + metric. No persistent queue.
- Address-book native-route delivery failure → expire cache entry → re-resolve next time.
- Shadow-DID determinism → restart reconstructs identical DIDs; no lost identity, no key persistence.

## Testing

- **Unit:** `ResendProvider::parse_webhook`/`verify_webhook` (real message, bounce, bad-sig fixtures); shadow-DID determinism (same email → same DID; different secret → different DID); address-book TTL + expire-on-failure; outbound dedup on `delivery_cid`.
- **Integration** (`repos/integration-tests/`, `MockProvider` impl):
  - inbound: POST webhook → block lands on resolved channel, signed by shadow DID;
  - outbound: post block to a channel with a shadow member → `MockProvider::send` captured it;
  - round-trip: email-in → block → second Jig user replies → email-out to original sender;
  - policy: bridge in `[bridges] deny_list` → webhook `5xx` / no submit;
  - dedup: double webhook → one block; double fanout fire → one email.
- **`BridgeStorage` SQLite impl:** put/get/delete/TTL-expiry/sweep unit tests in jig-server.

## Forward-state direction (not alpha.email scope)

- **Open-mode** (alpha.email.2): bridge resolves multiparty email threads → group channels; shadow-DIDs act as fuller participants rather than pure 1:1 delivery proxies. This iteration is **restricted-mode** — focused on getting blocks into the right 1:1 recipients' hands.
- **Storage tier:** when `repos/storage/` extraction lands (Postgres/Cockroach backends), the SQLite `BridgeStorage` impl is replaced/joined and `naively_single_backend_bridge_storage` is retired.
- **Admin verbs:** `jig bridge email <verb>` (email-bankruptcy, migrate) land in jig-cli in a later iteration; the retired standalone binary's subcommands are not reintroduced.
- **Attachments > 25 MB:** object-storage offload deferred; alpha.email enforces the inline-only 25 MB cap.
