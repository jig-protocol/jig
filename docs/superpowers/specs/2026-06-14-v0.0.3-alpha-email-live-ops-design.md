# v0.0.3-alpha.email-live (sub-project C) — live ops + E2E round-trip — design

**Status:** approved (brainstorm 2026-06-14)
**Builds on:** A (PR #19, merged) — Resend Receiving-API inbound fetch + deterministic managed-DID registration. B (PR #20, merged) — config-gated `[tls]` HTTPS serving (hand-wired on rustls 0.22), reqwest dedupe, tokio trim.

## Context: where C sits

The email-live work is decomposed A → B → C. A made the bridge fetch real inbound bodies; B gave jig-server a public-HTTPS edge. **C makes it actually live**: a real email → block → reply → email round-trip against a real Resend account on a real VPS, captured in a reusable runbook.

C is unusual: it is **mostly operational** (VPS, DNS, certs, Resend, secrets) but carries **two load-bearing code prerequisites** discovered during exploration. The canonical server is the `jig-server` crate in the open-source monorepo (`repos/jig-server/`); the legacy out-of-monorepo server and closed-source internal servers are NOT touched.

## Locked decisions (brainstorm 2026-06-14)

- **Scope:** prove it live once + produce a reusable runbook. Defers install.sh productionization, the release pipeline, and auto-ACME (those are "later", not C).
- **TLS edge:** use B's `[tls]` serving **directly** with a Let's Encrypt cert from `certbot`. Exercises B's edge; one process; valid cert for Resend's webhook POST.
- **Domain:** a **subdomain of jig.onl** — `mail.jig.onl` — for both `bridge_domain` and the webhook host.
- **VPS:** an existing Linux box (operator-provided OS/IP/access).
- **Resend inbound:** account state is **unknown** → an explicit **feasibility gate** runs first; if email-receiving is gated, C still proves outbound live and documents inbound as blocked-on-Resend.
- **Secrets:** add **`${ENV}` expansion** to the bridge config loader (fulfilling the existing code comment), injected via `systemd` `EnvironmentFile`/`op` — nothing secret on disk or in git.

## Phase 1 — code prerequisites (one reviewable PR)

The only testable code in C. Kept as a separate PR so the un-testable live ops stay out of code review. Executed subagent-driven (same as A/B), mirroring CI on stable.

### C1 — wire real `JigServerConfig` loading in `main.rs`

**Goal:** the operator's `[bridge.email]` / `[federation]` / `[identity]` / `[server]` actually take effect.

- Add a loader to `JigServerConfig` (`repos/jig-config/src/v0_0_2_server.rs`): `pub fn load(path: &Path) -> anyhow::Result<Self>` = read file + `toml::from_str`. It already derives `Deserialize` + `Default`, so this is a thin wrapper. Unit-test it parses a file with `[bridges.per_bridge.email]` + `[federation]`.
- `main.rs`: when a config path is resolved (the `args.config` path, else the same well-known resolution `ServerConfig` uses — cwd config, then `~/.jig/config.toml`), load `JigServerConfig` from **that same path** and pass it to `v0_0_2::AppState::new(...)` instead of `JigServerConfig::default()`. On load failure, log + fall back to default (don't crash a v0.0.1-only deploy that has no v0.0.2 sections). When no config file exists at all, keep today's `::default()` behavior.
- **Bind reconciliation:** `ServerConfig` remains authoritative for the actual listener (`bind_address`/`port`/`[tls]`). `[server].listen` in `JigServerConfig` is **informational** for the v0.0.2 path; document that the operator sets the public bind via the root `bind_address`/`port` (+ `[tls]`), and `[server].listen` should be set consistently but is not the bind source. (Confirm in the plan that nothing load-bearing — e.g. an advertised discovery URL — derives the public host solely from `[server].listen`; if it does, ensure it reflects `mail.jig.onl`.)
- Test: a config file carrying `[bridges.per_bridge.email]` with `enabled = true` + a `[bridges.per_bridge.email.config]` table yields an `AppState` whose `start_configured_bridges` builds the email bridge (using a mock/stub provider or asserting the bridge is registered) — i.e. config from disk reaches the bridge.

### C2 — `${ENV}` expansion in `EmailBridgeConfig`

**Goal:** secrets come from the environment (systemd `EnvironmentFile`/`op`), never from disk/git.

- In `EmailBridgeConfig::from_toml` (after deserialization), resolve the secret-bearing fields `bridge_secret`, `resend_api_key`, `resend_webhook_secret`: if a field's value matches exactly `${VAR}` (regex `^\$\{([A-Za-z_][A-Za-z0-9_]*)\}$`), replace it with `std::env::var("VAR")`, returning an error if the var is unset; otherwise keep the literal. Whole-string match only (not substring) — keeps literal test values (`rk_test`) untouched.
- Apply to the `Option<String>` secrets when `Some`. `bridge_secret` is required (non-Option) — resolve it too.
- Tests: `${VAR}` resolves from a set env var; unset `${VAR}` → error mentioning the var name; literal values pass through unchanged; a non-`${...}` literal containing a `$` is left literal.
- Also fix the stale doc comment in `config.rs` (top-of-file `[bridge.email.config]` → the real `[bridges.per_bridge.email.config]` path).

### Phase 1 acceptance gate

Mirror CI on the **stable** toolchain (the local default is nightly): scoped `cargo +stable fmt --check` + `clippy -D warnings` (CI's package list) + `nextest` (incl. the new C1/C2 tests) + wasm-build + `cargo deny check`. Then push + open a PR against `main`. Sign via 1Password (no `--no-gpg-sign`).

## Phase 2 — live ops (guided; produces the runbook)

Operator-executed steps (real VPS/DNS/secrets/Resend dashboard) — not subagent-automatable. Each step is captured verbatim in the runbook as it's performed.

1. **Resend feasibility gate (do first).** Confirm email-*receiving* (inbound) is enabled on the plan: a verified domain that supports receiving, the ability to set an inbound route + webhook. If unavailable/gated, **stop the inbound thread** and proceed with outbound-only (Phase 3 outbound), documenting the inbound block.
2. **DNS for `mail.jig.onl`:**
   - `A` record `mail.jig.onl` → VPS public IP (the HTTPS webhook host).
   - Resend **sending** records on the domain: SPF (`TXT`), DKIM (`TXT` / CNAMEs per Resend), DMARC (`TXT`).
   - Resend **receiving**: `MX` for `mail.jig.onl` → Resend's inbound MX (per Resend dashboard).
3. **TLS:** install `certbot`; issue a Let's Encrypt cert for `mail.jig.onl` (standalone or webroot — standalone needs `:80` briefly). Point `[tls] cert_path`/`key_path` at the issued `fullchain.pem`/`privkey.pem`. **Caveat:** jig-server reads the cert at startup only (no hot-reload) — cert renewal requires a service restart; document `certbot renew --deploy-hook "systemctl restart jig-server"`.
4. **Secrets + service:** create a `jig-server` `systemd` unit; supply secrets through an `EnvironmentFile` rendered from 1Password (`op read`/`op run` with a service-account token) holding `JIG_BRIDGE_SECRET`, `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`. The config references them as `${...}` (C2).
5. **Production `config.toml`:** root `bind_address = "0.0.0.0"`, `port = 443`, `[tls] enabled = true` + cert paths. Enable the bridge with `[bridges.per_bridge.email]` `enabled = true`; put the `EmailBridgeConfig` fields under its `[bridges.per_bridge.email.config]` sub-table: `bridge_domain = "mail.jig.onl"`, `provider = "resend"`, `bridge_secret = "${JIG_BRIDGE_SECRET}"`, `resend_api_key = "${RESEND_API_KEY}"`, `resend_webhook_secret = "${RESEND_WEBHOOK_SECRET}"`. Set `[identity]`/`[server]` for the public host. (`bridge_permitted("email")` requires `enabled = true` and not denied — per `v0_0_2_server.rs::bridge_permitted`.) Install the binary by building from the source checkout on the VPS (`git clone` + `cargo build --release`, matching install.sh's source path — no release pipeline).
6. **Resend config:** verify the domain; register the inbound webhook → `https://mail.jig.onl/_bridge/email/inbound`; capture the webhook signing secret into 1Password.
7. **Boot:** `systemctl start jig-server`; confirm it binds `:443` over TLS (B's path), `/.well-known/jig` is reachable over HTTPS, and the bridge logged as started.

## Phase 3 — prove + capture

- **Outbound (always provable):**
  - Run the `#[ignore]` live smoke against the real key: `RESEND_API_KEY=… RESEND_TEST_TO=… cargo test -p jig-bridge-email --ignored send_live` (exact name per `resend.rs`). Confirms sending works against the live account/domain.
  - Real end-to-end: an internal jig CLI user posts in a channel with a managed email member → bridge sends an email to the external address.
- **Inbound round-trip (if feasibility gate passed):** email `name@mail.jig.onl` from the operator's personal mailbox → Resend receives (MX) → POSTs the webhook → bridge verifies (Svix) + `fetch_inbound` (Receiving API) → creates the managed DID + the deterministic 1:1 DM channel → ingests the block → the operator's jig CLI (pointed at `wss://mail.jig.onl`, a member of that channel per the bridge's 1:1 model) sees it → **reply** → bridge translates → outbound email back to the mailbox. Exact managed-address↔channel↔internal-user mapping follows the bridge's existing restricted 1:1 model (confirmed during planning).
- **Endpoints:** external = the operator's personal email; internal = a jig CLI (laptop or VPS) on the live server.
- **Deliverable:** a runbook at `docs/deployment/` (e.g. `email-bridge-live.md`) capturing every Phase 2/3 step verbatim — DNS records, certbot commands, the systemd unit, the `op` secret wiring, the config.toml, Resend dashboard settings, and the exact test commands + observed round-trip — so the deploy is repeatable. Include the deferred list.

## Testing

- **Phase 1:** C1 + C2 unit tests (config-from-disk reaches the bridge; `${ENV}` resolution/error/literal). Full CI-mirror gate green.
- **Phase 3:** the live round-trip is the integration test; the `#[ignore]` live smoke is the automated outbound check. No new always-on tests for the ops layer — the runbook + the manual round-trip are the evidence.

## Deferred (explicitly out of C scope)

- `install.sh` productionization (public bind, TLS/domain prompts, systemd) — a turnkey-deploy sub-project.
- Release pipeline (cut signed tarballs to `releases.jig.onl`) so `curl|sh` works end-to-end.
- In-process auto-ACME (rustls-acme) + TLS cert **hot-reload** (today renewal needs a restart).
- Federation single-rustls dedup (tracked: memory `jig-federation-rustls-dedup-followup` + task chip) — do after C.
- Multi-instance/scaling, monitoring, log shipping.

## Acceptance

- **Phase 1:** the two code changes land as a merged PR; CI-mirror gate green.
- **Phase 2/3:** jig-server runs live on `mail.jig.onl` over HTTPS; the outbound path is demonstrably live (smoke + real send); the inbound round-trip works end-to-end **or** is documented as blocked on Resend receiving with the outbound path proven. The runbook captures the whole deploy.
