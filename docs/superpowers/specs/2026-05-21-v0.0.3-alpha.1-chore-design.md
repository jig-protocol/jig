### alpha.1a — `bridges/` namespace + `jig-bridge-core` trait

**Why this PR exists:** The current `repos/jig-email-bridge/` crate violates the agreed "no first-class bridges" naming convention (`jig-bridge-<X>`, not `jig-<X>-bridge`). The top-level `repos/` directory is also already 12 dirs and will balloon as we add slack, irc, ssh, matrix bridges. Both need fixing before any v0.0.3 work imports `jig-bridge-*` paths.

**Changes:**

- New top-level dir `repos/bridges/`; workspace gains `members = ["bridges/*", ...]` glob (no Cargo.toml edits when new bridges land)
- New crate `jig-bridge-core` at `repos/bridges/core/`: exports the `Bridge` trait, `BridgeContext`, `SubmitHandle`, `SubscribeHandle`
- Move `repos/jig-email-bridge/` → `repos/bridges/email/`; rename crate `jig-email-bridge` → `jig-bridge-email`
- Update 19 file references (Cargo.toml workspace member entry, README.md, IMPLEMENTATION_PLAN docs, install.sh, real_integration_test.sh, jig-client lib doc-comment, jig-config plan, jig-docs plan)
- `jig-bridge-email` keeps its current external-process binary shape in alpha.1a. Bridge trait is exported and tested with a noop impl. The actual in-process migration is alpha.email's job.

**Bridge trait (locked shape):**

```rust
// repos/bridges/core/src/lib.rs
pub trait Bridge: Send + Sync {
    /// Stable bridge identifier ("email", "slack", "irc"). Maps to
    /// `[bridge.<name>]` config and `jig bridge <name> <verb>` CLI.
    fn name(&self) -> &'static str;

    /// Bridge owns its external transport (SMTP server, Slack websocket, etc.)
    /// and uses `ctx` to push translated blocks back to the server.
    /// Server runtime calls this once at startup; bridge spawns its own tasks.
    async fn start(&mut self, ctx: BridgeContext) -> Result<()>;

    /// Server runtime calls this whenever a delivered block on a bridged
    /// channel needs to flow OUT to the external world. Bridge translates
    /// and emits via its transport.
    async fn outbound(&self, block: &DeliveredBlock) -> Result<()>;

    /// Clean shutdown — flush in-flight messages, close transports.
    async fn shutdown(&mut self) -> Result<()>;
}

pub struct BridgeContext {
    /// Bridge submits inbound-translated blocks via this handle.
    pub submit: SubmitHandle,
    /// Channel-scoped subscriptions if the bridge needs to watch state changes.
    pub subscribe: SubscribeHandle,
    /// Bridge-specific config slice from `[bridge.<name>]` in jig-server config.
    pub config: toml::Value,
}
```

**Listener ownership:** Bridge owns its own loop. Server runtime stays transport-agnostic — it has no opinion on whether the bridge listens on SMTP, polls IMAP, or holds a Slack websocket open. The trait makes the **translation step** (`event → blocks → submit`) explicit and testable; the listener loop is bridge-specific.

### alpha.1b — `trust-dns` → `hickory-dns` dep migration

**Why this PR exists:** `trust-dns-proto 0.23` pulls in `ring 0.16` (legacy, non-SPDX license expression, unsound `RUSTSEC-2021-0145`). The whole `trust-dns` family was renamed to `hickory-dns` and modernized; the upgrade clears ~6 pinned RUSTSEC advisories and the entire `OpenSSL` + ring `[[licenses.clarify]]` block in `deny.toml`.

trust-dns is used by jig-server (federation peer DNS), jig-nameserver (alias resolution), and jig-bridge-email (MX lookup for outbound email). Migration is mechanical: rename `trust_dns_resolver` → `hickory_resolver`, bump version, run tests.

**Changes:**

- Replace `trust-dns-resolver` with `hickory-resolver` in: `repos/jig-server/Cargo.toml`, `repos/jig-nameserver/Cargo.toml`, `repos/bridges/email/Cargo.toml`
- Rename imports throughout (`use trust_dns_resolver::...` → `use hickory_resolver::...`)
- Remove `OpenSSL` from `deny.toml` `[licenses] allow`
- Drop `[[licenses.clarify]]` block for ring
- Prune RUSTSEC ignores that trace back to ring/trust-dns (run `cargo deny check` and remove entries that no longer trigger)
- Verify CI `license-compliance` and `workspace` both stay green

## Forward-state direction (informs structure choices in this PR; **not** scope for alpha.1)

Two patterns this PR locks in that will recycle across subsequent v0.0.3 work:

**1. `<namespace>/core/` + `<namespace>/<specific>/` extraction pattern.**
- `repos/bridges/core/` + `repos/bridges/{email, slack, irc, ssh, matrix, ...}/`
- `repos/storage/core/` + `repos/storage/{sqlite, postgres, cockroachdb, scylladb, ...}/` (future)
- `repos/analytics/core/` + `repos/analytics/{duckdb, clickhouse, parquet, ...}/` (future)
- `repos/telemetry/core/` + `repos/telemetry/{otel, prometheus, ...}/` (future)

Each `core/` exports a trait + shared plumbing; specific crates implement against it. jig-server loads concrete backends via config rather than feature flags. This is the "0→60 curl install" target: small/simple individual-user defaults (sqlite, no analytics, no extra transports), with aggressive backends available for hyperscale operators (`jig.onl`'s central nameserver, etc.) via config + sibling-crate dependencies.

**2. Fast-follow `bridge-irc` and `bridge-ssh` after `bridge-email` lands.**
The composability of `jig-bridge-core` is theoretical until three real bridges exist. Shipping `bridge-irc` and `bridge-ssh` shortly after `bridge-email` stress-tests the trait against wildly different transport semantics (SMTP push vs IRC long-poll vs SSH session-oriented) and surfaces crossover issues empirically rather than via prediction. These are post-alpha.1 / post-alpha.email work but worth noting in the trait design.

## Error handling

The Bridge trait's `Result<T>` is `anyhow::Result<T>` at the binary edge. Bridge implementations use `thiserror`-derived domain errors internally and convert to `anyhow` when crossing the trait boundary. Same pattern as elsewhere in the workspace.
