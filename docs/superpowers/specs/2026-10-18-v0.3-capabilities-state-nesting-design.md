## Goal

The phase-2 exit criterion's second half: **a nested block composes with capability attenuation
verified by tests.** Concretely, at the end of this work:

- A block reaches a host function only if its manifest asks for it **and** someone with
  authority over the resource granted it. Anything else fails before the block's first
  instruction runs.
- A bot installed in a channel keeps state across invocations, and every state transition is in
  a signed receipt that names the state before and after.
- A bot posts into its channel through `ingest`, under the same gates as a person.
- A block invokes a child block by CID. The child gets at most what the parent holds, minus what
  the parent withholds, and its fuel and memory come out of the parent's budget.
- Tests prove each of those, including the negative cases.

### Out of scope for v0.3

- **Network access** (`net.fetch`). The roadmap's phase-2 list is storage, fetch-by-CID,
  post-message and timer. Arbitrary HTTP is non-deterministic and an exfiltration channel; it
  needs a recorded-response design of its own.
- **`crypto.sign`, `crypto.verify`, `external_process`.** The spec lists them; nothing needs them
  in v0.3. `external_process` should go from the spec outright.
- **Capabilities passed in messages** (phase 6 object capabilities). The design keeps the door
  open (grants are data with a defined attenuation order), but no block hands a capability to
  another at runtime in v0.3.
- **Phase-3 UI** (`jig:ui`), per lane A.
- **Pricing.** Fuel stays local telemetry ([fuel portability](../../investigations/2026-08-11-fuel-portability.md)).

## Baseline, verified against `main` at `d16f26a`

- **Nothing executes third-party code.** `BlockExecutor` (`jig-pipeline/src/executor.rs`) runs
  only the server's own `text-render` module, deliberately: a sender who chose the code would
  choose their own `render_hash`.
- **The only `Linker` adds WASI preview 1** (`jig-runtime/src/api.rs:481`), so today any import
  WASI p1 offers is ambient.
- **Capability scaffolding enforces nothing.** `capability_dsl`, both `CapabilityRegistry`s and
  `lint` have no production callers; L2 is deleting them. This design reuses none of it.
- **Three vocabularies disagree:** `net:http:fetch` (registry), `net.fetch` (spec),
  `jig_host::net::fetch` (jig-config). None names a timer or fetch-by-CID.
- **The manifest already has `capabilities: Vec<Capability>`** with `name`, `scope:
  Vec<pattern>`, `fuel`, `attestations`, `metadata` (`jig-core/src/manifest.rs:80`). Scope is a
  list of strings, so attenuation over it is glob containment.
- **A block CID hashes manifest, code and resources together** (`jig-core/src/bundle.rs`). The
  manifest carries `hlc_ts` and `metadata`, so two deployments of the same code have different
  CIDs, and there is no separate code CID.
- **`ingest` requires an author signature** over the manifest and code, then admission, identity,
  kind whitelist, channel existence, write authorization (membership on restricted channels), MLS
  gate, receipt, effect, persist, fanout (`jig-pipeline/src/ingest.rs:266`).
- **`GET /api/v1/blocks/{cid}` runs the channel read gate** of the block's channel for the caller.
  A CID is not a secret, so fetch-by-CID inside a block needs the same gate under some principal.
- **No per-block state.** `bridge_kv` is keyed by bridge name and is server-internal.
- **Encrypted blocks get a `0.3-sealed` receipt** and are never executed (SC-03).
- **Pooling allocator:** `total_core_instances = total_memories = max_concurrent_instances`,
  `max_memories_per_module = 1` (`jig-runtime/src/engine.rs:301`). The executor's `Slots` gate
  holds one permit per execution.

## Prior art, and what each one gives this design

| System | Relevant idea | Taken here |
| --- | --- | --- |
| WASI 0.2 / Component Model | No ambient authority: a component reaches only what it imports, and the host decides what each import is. Resources are unforgeable handles in a per-instance table. | Capabilities **are** WIT interfaces; link-time denial |
| wasmtime `component::Linker`, `InstancePre` | Instantiation fails if an import has no definition. `instantiate_pre` type-checks once and makes later instantiation cheap. `define_unknown_imports_as_traps` exists and must never be used. | One cached `InstancePre` per (code, granted interface set) |
| Object capabilities (E, KeyKOS, seL4) | Authority only by holding a reference; attenuation by wrapping one | Grants as data with a meet; v0.3 stops short of passing them |
| Macaroons, UCAN | A delegated token can only add caveats; a chain of proofs shows each step is a subset of the last | Attenuation is a meet, checked at each step; the grant chain is recorded in the receipt |
| Fuchsia component manifests | A parent `offer`s capabilities to a child; a child `use`s only what it was offered; routing is static and checked at resolve time | Children declared in the manifest; grants routed at install, not at call time |
| CosmWasm | A contract returns messages for the chain to dispatch instead of calling out; submessages and replies for composition; per-contract storage | Lane A's effects-returned `handle`; state as a pure fold |
| EVM | `CALL` forwards a capped share of gas; `STATICCALL` removes write authority; a call depth limit; per-contract storage | Child budgets carved from the parent's; depth limit; read-only children |
| Cloudflare Durable Objects | One alarm per object, `setAlarm` replaces it; one writer per object | Timer as one pending alarm per instance; single-writer state |
| Spin, wasmCloud | Manifest-declared outbound hosts and KV stores per component; capability providers linked by WIT interface | Interface-named capabilities with typed scopes |

## The model in one page

**Three things decide what a block may do, and the effective authority is their intersection:**

1. **The manifest requests** a set of capabilities: a ceiling the author signs. It is not
   authority. AB-04's "receives only the capabilities its manifest names" is necessary, not
   sufficient: a manifest asking to post into `#ops` gives it nothing in `#ops`.
2. **A grant gives.** A principal with authority over the resource (the channel owner for
   posting into a channel) signs a grant naming the block and a subset of what it requested.
   For a bot that grant is the **install** (Q3). For a child it is the parent's offer (Q5).
3. **Host policy limits** what this server will run at all (fuel ceilings, which interfaces it
   offers, reputation tiers).

`effective = request ⊓ grant ⊓ policy`, and for a child, `effective(child) = request(child) ⊓
offer(parent → child) ⊓ effective(parent)`.

**Two kinds of capability, enforced at three points:**

| Kind | Example | Enforced |
| --- | --- | --- |
| **Import** (the block calls the host during execution) | fetch-by-CID, invoke child | (a) **at link time:** an interface not granted is absent from the linker, so instantiation fails; (b) **at call time:** the host function checks the scope (which CIDs, which channels) |
| **Effect** (the block returns it; the host applies it after) | post-message, set-state, set-timer | (c) **at apply time:** each returned effect is checked against the grant, then goes through `ingest` or the state store |

Link time alone cannot enforce scopes (they are data, not types) and cannot enforce effects (they
are return values, not calls). All three points fail closed. In lane A's outcome terms (#112 Q3):

- A refusal at (a) or (b) makes the run **`incomplete`** (reason `capability-refused`). It depends
  on the grant, not the block, so it is never compared. At install it is a refusal, not a run.
- A refusal at (c) does not change the run's outcome. The run is `ok` and its effect list is
  hashed like any output; the receipt records, separately, which effects the host applied and
  which it refused and why. Keeping "what the block computed" apart from "what this host let
  it do" means two hosts with different grants still agree on the run.

**Lane A's effects-returned model removes most imports.** Of the roadmap's four host functions,
only fetch-by-CID has to be an import. State, posting and timers are all effects. That leaves a
host import surface of two interfaces in v0.3 (`blocks` and `compose`), which is the smallest
attack surface this could have, and it makes `handle` close to a pure function of
`(state, invocation, fetched blocks) → (state', effects)`, which is what makes replay possible.

## Q1. Vocabulary: one name per capability, a grammar, scopes, and where it lives

| Option | Shape | For | Against |
| --- | --- | --- | --- |
| **A. WIT interface names (recommended)** | `jig:host/blocks@0.1.0` for imports; effect capabilities named by their variant, `jig:host/effects.post@0.1.0` | One vocabulary: the string in the manifest is the string the linker matches. Versioning is WIT semver. Nothing to map, so nothing to disagree. | Effect names need a convention, since they are not interfaces |
| B. Dotted names (`storage.read`, `message.emit`) mapped to interfaces | Today's spec | Readable; existing spec text | A mapping table is exactly what produced three disagreeing vocabularies |
| C. URIs (`https://jig.dev/cap/storage/read`) | | Globally unique, extensible by third parties | Verbose; still needs a mapping to WIT |

**Recommendation: A.** Names are `<package>/<interface>[.<effect>]@<semver>`, the effect suffix
only for effect capabilities. A host matches the package and interface exactly and the version by
semver compatibility (same major, or same minor while `0.x`). An unknown name fails closed.

**Scopes become typed, not lists of glob strings.** Each capability's scope has a schema in the
spec, and every field has an attenuation order so that `⊑` (at most) and `⊓` (meet) are defined
and decidable:

| Field type | `a ⊑ b` when | Meet |
| --- | --- | --- |
| Set (channel ids, CIDs) | `a ⊆ b` | intersection |
| Quota (bytes, count, interval floor) | `a ≤ b` (or `≥` for a floor) | min (or max) |
| Flag (`read_only`) | `a` implies `b` | and |

An unknown scope field fails closed, so a scope written for a later version never silently
widens. Globs are out: glob containment is decidable for simple patterns but easy to get wrong,
and v0.3 needs none (channels and CIDs are exact names). `net.fetch` can bring a URL-prefix type
when it comes.

**The v0.3 vocabulary:**

| Name | Kind | Scope | Notes |
| --- | --- | --- | --- |
| `jig:host/blocks@0.1.0` | import | `channels: set<channel-id>`, `cids: set<cid>`, `max_bytes: quota` | fetch-by-CID (Q3) |
| `jig:host/compose@0.1.0` | import | `children: set<cid>`, `max_depth: quota` | invoke a child (Q5) |
| `jig:host/effects.post@0.1.0` | effect | `channels: set<channel-id>`, `per_invocation: quota`, `per_hour: quota` | Q3 |
| `jig:host/effects.state@0.1.0` | effect | `max_bytes: quota` | Q4 |
| `jig:host/effects.timer@0.1.0` | effect | `min_interval_ms: floor`, `max_horizon_ms: quota` | Q3 |

**Where it lives:** the WIT files are normative at `repos/jig-spec/wit/jig-host/`, beside A's
`jig-block/`. `block-execution.md`'s capability section is rewritten to this table plus the scope
schemas, and drops `net.fetch`, `storage.read`/`storage.write`, `message.emit`, `crypto.*`,
`timer` and `external_process` (the first five as "not in v0.3", the last outright). The manifest
`Capability` struct changes `scope: Vec<pattern>` to a typed scope object; old manifests with a
non-empty `capabilities` array are refused, which costs nothing because no deployed block uses
one.

**What would change it:** a need for third-party capability namespaces in v0.3 (then C's URIs,
mapped once into WIT package names).

## Q2. Enforcement at link time

| Option | How | For | Against |
| --- | --- | --- | --- |
| **A. Linker per granted interface set, plus call-time scope checks (recommended)** | Build a `component::Linker` holding only the granted interfaces; `instantiate_pre` once per (code hash, granted set) and cache the `InstancePre`; host functions check scopes on each call | Denial is structural: an ungranted function does not exist in the instance, so a bug in a check cannot expose it. `InstancePre` makes it as cheap as today's pre-compile | A cache key per grant shape (small: there are five capabilities) |
| B. One full linker; refuse at validation if imports ⊄ grant | Read `Component::component_type().imports()` and compare | One linker; a clear early error | A bug in the comparison is a hole, because the functions are all there |
| C. One full linker; every host function checks the grant | Runtime checks only | Simplest to write | Ambient authority with guards: exactly what AB-04 rules out |

**Recommendation: A, with B's check as well,** run at install and at ingest so that a block
whose imports exceed what can be granted is refused with a clear error before anyone tries to
instantiate it. Rules that go with it:

- **No `wasi:*` imports in v0.3.** Not clocks, random, filesystem, environment or stdio. Time is
  in the invocation; randomness, if ever, is derived from it. Lane A's profile `jig-det-1` (#112
  Q2) already says this and picks `wasm32-unknown-unknown` plus `ComponentEncoder`, which gives a
  component with zero imports; this design adds only the `jig:host/*` lines.
- **Never `define_unknown_imports_as_traps`** or any "stub what's missing" helper; a test asserts
  that a component importing an ungranted interface fails to instantiate.
- **The WASI p1 linker in `api.rs` leaves the block path.** Whatever stays of the p1 path (the
  CLI's local runner, if L3 keeps it) must not be the path that runs third-party blocks.
- **Instantiation failure is an `incomplete` run** (reason `capability-refused`, naming the
  interface), and at install time it is a refusal, not a run.

**What would change it:** if the number of distinct grant shapes grows past a few dozen (it won't
in v0.3), cache by interface set only and keep scopes at call time, which is already the design.

## Q3. Host-function semantics

### fetch-by-CID (`jig:host/blocks`)

`fetch(cid) -> result<payload, fetch-error>` returns the block's canonical bundle bytes, or
`not-found`, `not-granted` or `too-large`.

- **Verified addressing:** the host recomputes the CID over the bytes it returns and treats a
  mismatch as `not-found` (and logs it as store corruption). Local today, but the same function
  will serve blocks that arrived by federation.
- **Under whose authority?** Not the server's (it can read everything) and not the invoking
  user's (that makes the bot a confused deputy for whoever triggered it). **The grant's:** a
  block may fetch a CID only if it is in the grant's `cids`, or it lives in one of the grant's
  `channels`. For a bot, those channels are the ones it is installed in, so it reads nothing
  its installer could not already show it.
- **Encrypted content: refused on the server.** A block in an encrypted channel is ciphertext;
  handing it to a bot is useless and leaks metadata, and handing it to `compose` would be
  executing encrypted content (SC-03). The server returns `not-found` for blocks in channels
  whose suite is not `none`. On a client (Q6) the question doesn't arise in v0.3.
- **Determinism:** fetched content is fixed by its CID, but whether a CID is *available* depends
  on the host. The receipt lists every fetch with its outcome (`[cid, ok|not-found|…]`); a
  replay is valid against that list, and a verifier who lacks a fetched block knows exactly
  which one.

Options considered: (b) fetch under the invoking user's read authority (rejected: confused
deputy); (c) fetch only CIDs pinned in the manifest (safe and fully verifiable, but a bot that
reads the message it is replying to needs channel scope, so `cids` stays as the pinned option
within A).

### post-message (`effects.post`)

`handle` returns `post { channel, payload }`. The host builds a block from it and runs it through
`ingest` like any other write, so the write gate, MLS gate, rate limits, receipts and fanout all
apply unchanged. The open question is **whose signature it carries**, since `ingest` requires the
author's signature and a block cannot hold a secret key (its code is public).

| Option | Author DID | For | Against |
| --- | --- | --- | --- |
| **A. Each installed bot gets its own DID; the host holds its key (recommended)** | `did:jig:<instance key>`, minted at install | Reuses every gate: the owner adds the bot DID as a member like anyone; rate limits, admission and reputation apply per bot; abuse is attributable to that bot, not the server or the user | Host-custodied key: the host can post as the bot. That is honest (it runs the bot and could make it say anything anyway) but must be stated, and the bot's DID document must say who controls it |
| B. The server signs as itself, with `on_behalf_of: <instance>` | server DID | No new keys | Server DID becomes a channel member and author of content; every bot on a server shares one identity, rate limit and reputation |
| C. The invoking user signs | user DID | Clear accountability | The user is offline when the timer fires; code would post as a person; impossible server-side without the user's key |

**Recommendation: A.** The install is a new block kind (`block-install`), signed by the channel
owner, naming the block CID, the grant and the bot's DID and public key, with the host's
countersignature that it holds the key. Its CID is the **instance id** (Q4). A posted block's
manifest carries `metadata.produced_by = {instance, invocation}`, and its receipt links back to
the invocation receipt, so a reader sees that code wrote it and which code.

Two consequences DJ should see now:

- **Bot loops.** Bot X posts, which triggers bot Y, which posts, which triggers X. Each step is
  cheap and individually authorized. Recommendation: an invocation triggered by a bot-produced
  post carries a hop count from the post's `produced_by`; the host refuses to invoke past a
  small limit (proposal: 4), and a bot is never invoked by its own posts. This needs a threat
  register entry (proposed **AB-07**, below).
- **What triggers a bot** (every message, mentions, a command prefix) is install configuration,
  not a capability. It belongs to lane A's `invocation` or lane Dv; this design only needs it to
  be in the install block so a replay knows why the bot ran.

### timer (`effects.timer`)

`handle` returns `set-timer { after_ms, tag }` or `cancel-timer`. Later the host invokes `handle`
with an invocation whose input is `timer { tag }`.

- **One pending timer per instance; setting replaces it** (the Durable Objects alarm model). A
  bot that needs many schedules keeps them in its state and re-arms for the earliest. This bounds
  host bookkeeping to one row per instance.
- **Deterministic replay:** the block never reads a clock. The time it sees is the invocation's
  `hlc`, which is **`ingest.ingest_hlc` of the triggering block, never the author's
  self-asserted `hlc_ts`** (TM-02; lane A's answer 4). `ingest` is the record DJ settled in L7's
  Q2: `{channel_id, seq, ingest_hlc, block_cid, prev}` signed by the channel's home server,
  travelling with the block and passed through unchanged by relays. A replay uses the recorded invocation, so
  when something happened is a recorded input, not something the replayer recomputes.
- **A timer fire is a block: kind `timer-fire`** (DJ's call on L7's Q1: the per-channel ingest
  record stays blocks-only). The owning server authors it with its own DID and ingests it like
  any block, so it gets an `ingest` record like every block and the invocation's clock is its
  `ingest.ingest_hlc`.
  Its manifest names:
  - `install`: the `block-install` CID, owner-signed, whose grant bounds the schedule
    (`min_interval_ms`, `max_horizon_ms`);
  - `set_by`: the receipt of the invocation whose returned `set-timer` armed this fire;
  - `scheduled_at`: the instant it was due, which is `set_by`'s `ingest.ingest_hlc` plus `after_ms`;
  - `tag`: the bytes the bot passed, which become the invocation's input.
- **A client can check each fire against its schedule:** `scheduled_at` is what `set_by` says;
  `after_ms` is within the install's bounds; no invocation of the same instance between
  `set_by` and the fire (by `ingest.seq`) replaced or cancelled the timer; and the fire's own
  `ingest.ingest_hlc` is at or after `scheduled_at`. `ingest.prev` makes a dropped record a
  visible gap, but a fire that was simply never authored leaves no gap. A fire that fails any check is evidence
  against the owner.
- **Trust level: the owning server's word alone.** No one else signs a timer fire, so a hostile
  owner can drop it, delay it, or fire one the schedule did not call for under a fabricated
  `set_by` it also controls. The checks above catch a fire that contradicts the signed record;
  they cannot catch a fire never sent or one sent late. The chain makes that attributable after
  the fact; it does not prevent it. Bot state driven by timers is only as honest as the owning
  server (the same bound as Q4's single writer, OP-07).
- **Visibility:** a `timer-fire` lives in the bot's channel and is fanned out like any block. Its
  `tag` is bot-chosen bytes that may reveal bot state, which is acceptable only because bots run
  in open channels in v0.3 (Q6).
- **Federation: only the channel's owning server (its home server) fires timers** (D24: one owner per channel),
  and only it runs the bot at all (Q4). Otherwise every server holding the channel fires it and
  the bot posts N times.
- Scope: `min_interval_ms` floor, `max_horizon_ms`. Missed fires (the server was down) fire once
  on recovery, not once per missed interval.

Options considered for timers: (b) a `timer` import that blocks or yields (rejected: async in the
guest, non-deterministic); (c) cron expressions in the install (simpler for authors, but a
second scheduling language in the spec; a bot can implement cron in its state).

## Q4. State model

### What state is keyed by

| Option | Key | For | Against |
| --- | --- | --- | --- |
| **A. Per install (recommended)** | the `block-install` CID | An install is one block in one channel under one grant, so "per block and channel" falls out. Upgrades are explicit: a new install names `inherits_state_from` and the old owner signs it | A reinstall starts empty unless it inherits |
| B. Per block CID, shared across channels | block CID | One bot, one memory | **A data path out of restricted channels:** the bot reads in `#private` and writes the same state it reads in `#public` |
| C. Per (block CID, channel) | pair | Same isolation as A | No identity for "this deployment"; a different grant to the same pair is ambiguous |

Since the block CID covers the manifest, B and C would also lose state on any manifest change, so
the only stable identity is one that the installer chooses: the install.

### Shape and transitions

**Recommendation: state is one blob, passed in and returned (a pure fold).** `handle` receives
the current state as an argument and may return `set-state(bytes)`. No import.

- `state_cid = blake3(state bytes)`; the empty state has a fixed CID.
- Each invocation's receipt records `state_before` and, if changed, `state_after`. Successive
  receipts form a hash chain per instance: `state_before` of one is `state_after` of the
  previous. A gap or a fork in that chain is visible to anyone holding the receipts.
- Cap: `effects.state.max_bytes`, default 64 KiB, host policy ceiling 1 MiB. Copying it in and
  out per call is cheap at that size.
- A run whose outcome is `error` or `incomplete` changes no state and applies no effects:
  state and effects commit together or not at all, in the same transaction as the posted blocks'
  ingest where possible.

Options considered: (b) a key-value import with reads as calls and writes as effects (scales to
larger state, but reads become part of the replay transcript and the receipt needs a state root
over a tree; good for v0.4 if 1 MiB proves too small); (c) a CRDT state that several servers
write (needed only for multi-writer, which A avoids).

### Who stores it, ordering, conflicts

- **The channel's owning server runs the bot and stores its state.** One writer, so there is no
  conflict to resolve and HLC is not used to merge anything. Invocations are ordered by their
  triggers' `ingest.seq`, and each receipt names its trigger's `ingest` record, so the state
  chain and the channel's record chain can be checked against each other.
- **The cost of one writer is trust in it.** The owner can withhold, reorder or rewrite state,
  exactly as it can withhold or reorder messages today (OP-07). The chain makes rewriting
  detectable by anyone holding earlier receipts; it does not prevent it. Proposed text for
  OP-07's mitigation column says so.
- Other servers federating the channel receive the bot's posts as ordinary blocks and never run
  the bot. When F's channel contract lands, "who runs a channel's bots" is a contract term with
  this answer as the default.
- The state store is a new table keyed by instance id holding the current blob and its CID. The
  receipts are the history; the table is not.
- **Channels are named by id, not slug.** Lane F settled that a channel is identified by the CID
  of its `channel-create` block alone. Grants (`channels: set<channel-id>`), installs and
  `fetch` scopes use that id; a slug is display only, so renaming or re-homing a channel never
  changes what a grant reaches.

### When the sequencer moves

Lane F lets the channel owner move the sequencing (home) server with an owner-only
`sequencer-set` block, and the `ingest` chain continues across the handover. The bot moves with
it, under these rules:

| What | Recommendation | Options considered |
| --- | --- | --- |
| **The bot itself** | **Reinstalled.** The bot's key is custodied by the old host (SC-04), and nothing should carry a private key between operators. The new sequencer runs a new `block-install`, owner-signed, with a new bot DID and `inherits_state_from: <old install>`. The new operator's policy must allow the block (#112 Q7); if it doesn't, the bot stops at the handover, and the owner sees why. | Move the key (rejected: a key that left one operator's custody is known to two); keep the old host running the bot remotely (rejected: the bot would be sequenced by one server and run by another, which brings back multi-writer) |
| **State** | **Travels by content address.** The new sequencer takes the state blob whose CID is the last `state_after` at or before the handover head, from the old host or any copy, and checks it against that CID. If no copy matches, it **replays** the instance's invocations from the receipts (every input is recorded, Q3/Q4), which is slow but verifiable. If neither works, the new install starts empty and says so in its manifest. | Always replay (correct but costly for long-lived bots); drop state on every move (simple, but a sequencer move then wipes every bot) |
| **Armed timers** | **Re-derived from the chain.** The live timer is the latest `set-timer` in the instance's receipts at or before the handover head that no later invocation replaced or cancelled. The new sequencer re-arms it with the same `scheduled_at`; if that has passed, it fires once on arrival. The `timer-fire` still cites the original `set_by`, so clients check it as before. | Drop armed timers (bots silently stop waking); have the old sequencer hand them over (trusts the old server for something the chain already records) |

**F's caveat: a partitioned old sequencer.** An old sequencer that has not seen the
`sequencer-set` can go on ingesting past the handover head, and running the bot there: firing
its timers, advancing its state and posting. Everything it does after the head is on a fork the
continuing chain does not include, so those writes are lost, as F says. For bots that means:

- the new sequencer starts from the state at the handover head and never merges fork-side
  state; a bot's fork-side posts and state transitions are discarded with the fork;
- the same timer can fire on both sides, so members may briefly see one fire twice; only the
  continuing chain's fire counts;
- two state chains from one instance past the same head are evidence that a sequencer kept
  running after it was replaced (a partition or misbehaviour), and clients surface it like any
  other fork.

Effects never commit ahead of their trigger's `ingest` record, so nothing a bot does on the fork
is applied to the continuing chain.

## Q5. Nesting

### How a parent invokes a child

| Option | Shape | For | Against |
| --- | --- | --- | --- |
| **A. Synchronous `compose.invoke(cid, input) -> result<payload, invoke-error>` over children declared in the manifest (recommended)** | The child runs to completion inside the parent's call | Composition reads like a function call; the child's output is data the parent decides about; the whole tree is in one receipt | Re-entrant instantiation inside a host call (verify in a spike) |
| B. Asynchronous: the parent returns `invoke` as an effect (CosmWasm submessages) | The host runs the child later and calls the parent back | No re-entrancy; natural for the actor model of phase 6 | Every composition becomes a state machine; latency per level |
| C. Dynamic: invoke any CID the parent can fetch | | Most flexible | **Compile amplification:** compiling a component costs ~16 ms of host CPU and none of it is metered as fuel, so a parent that invokes 1,000 distinct CIDs buys 16 s of host work for one invocation's fuel. Also, the installer cannot see what code the grant reaches |

**Recommendation: A, with children declared in the parent's manifest** (`children: [cid…]`,
covered by the parent's CID). The installer sees the whole tree at install, the host compiles and
validates every child at install, and an undeclared CID fails with `not-declared`. A child is a
`world component` (lane A's naming): it exports a pure function, returns a payload, and imports at
most what its parent offers. Children do **not** return effects in v0.3: a parent can only apply
effects it is itself granted, so a child's effects would add no authority, only ABI. Children are
stateless in v0.3 (a child's state would be keyed by parent instance and child slot; defer until
someone needs it).

### The attenuation algebra

- A grant is a map from capability name to typed scope (Q1). `⊑` and `⊓` are defined field by
  field; a capability absent from a grant is bottom.
- **Offer:** the parent's manifest says, per child, what it offers: `offers: { <child cid>:
  <grant> }`. Withholding is not offering.
- **Child effective authority** = `request(child) ⊓ offer(parent → child) ⊓ effective(parent)`.
  Because `⊓` only shrinks, `effective(child) ⊑ effective(parent)` holds at every depth by
  construction, and the tests prove it rather than trust it.
- **Effects stay at the root.** Only the root instance's returned effects are applied, checked
  against the root's grant.

### Budgets

- **Fuel:** the child runs in the parent's `Store`, so it draws on the same counter. A per-child
  cap is set by saving the remaining fuel, setting `min(remaining, child_cap)` and restoring
  `remaining − used` on return.
- **Memory:** a `ResourceLimiter` on the store caps the total across every instance in the tree,
  so the parent's `max_memory_pages` bounds the tree, not each node.
- **Non-portable exhaustion is not observable by the parent.** If anything in the tree runs out
  of fuel, stack or epoch, the whole run is `incomplete` (lane A's #112 Q3); the parent never gets
  an error it could branch on. This matters because fuel and native stack use are not portable
  across engines, architectures or wasmtime patch versions: if a parent could catch "child ran
  out of fuel" and render something else, its output would depend on the host's engine, and two
  honest servers would sign different `output_hash`es. Stack is the subtle one: a synchronous
  child runs on the parent's native stack, so depth eats it.
- **Deterministic child failures are observable.** A child that returns `err(block-error)`, or
  traps deterministically (`unreachable`, an out-of-bounds access, memory past the share the
  parent gave it), gives the parent `invoke-error::failed(hash)` or `invoke-error::trapped`.
  These are the cases A classes as comparable `error` outcomes, so the parent may branch on them
  without breaking agreement.
- **Pool slots:** a tree of depth `d` holds up to `d + 1` instances at once (more, for components
  with several core modules). The executor's `Slots` gate takes one permit per execution and the
  pool is sized to `max_concurrent_instances`; if parents take permits and then wait for children,
  a burst of parents deadlocks. Lane A's answer 6 settles it: at admission the executor reserves
  the tree's worst-case slot count, computed from the pinned closure, all or nothing, and a tree
  too big for the pool is refused at upload.

### Fuel and host meters (lane L2's question from #109)

L2 asks whether host-function cost should be summed with wasm fuel into one `fuel_total`.
**Recommendation: no. Keep them as separate, labelled meters, both for enforcement and for
receipts; v0.3 has no `fuel_total`.**

| Option | For | Against |
| --- | --- | --- |
| **A. Separate meters (recommended):** wasm fuel bounds compute; each host import has its own quota in natural units (`fetch` bytes and calls, `compose` calls), set by the typed scope (Q1) | Quotas in bytes and calls mean the same on every engine and attenuate with the same meet as every other scope field; an engine upgrade cannot change what a grant allows | Several limits to set instead of one |
| B. One budget: host functions deduct a scheduled fuel cost from the store's counter | One number to set and to carve for children | The budget's meaning changes with every wasmtime patch (#112: fuel accounting changed within 49.x), so a grant that allowed 10 fetches yesterday allows 9 today; the receipt's number mixes engine units with schedule units |
| C. Separate meters, also summed for display | Compatibility with today's `receipts.md` | A sum of incomparable units invites exactly the comparison the fuel-portability doc forbids |

How it composes with parent-pays: a child's wasm fuel comes out of the parent's store counter
(above), and a child's host quotas are a meet of the parent's (an offer can only lower them), with
the child's use counted against the root's quota. The receipt carries `engine.fuel_used` (wasm
only, as #112 Q5 says) and a `host` object of named counters beside it, per node of the
`children` tree. Nothing is summed.

For #109 itself: its fix is right as a stopgap. `fuel_total` lives in the v0.2 `BlockReceipt`,
which A's deletion plan removes with ABI 2, so nothing should be built on the sum in the
meantime, and jig-core's validation requiring it goes with it.

### Depth, receipts, cycles

- **Depth limit:** 4 levels below the root, host-configurable lower, never higher in v0.3.
- **Cycles** are allowed and bounded by depth and fuel (a parent may declare itself as a child).
- **Child receipts are not separate signed objects or a new format.** Lane A's single v0.3
  receipt (#112 Q5) gains a `children` field on `kind: exec`: `children: [{cid, invocation_hash,
  outcome, fuel_used, children: […]}]`, signed once with the root. `outcome` uses A's
  `ok`/`error` hash or `incomplete` reason. The fuel numbers are telemetry, as everywhere else.
- **Composition is by the host, not by nested components.** Children are separate component
  instances that the host links with the attenuated grant, so `jig-det-1`'s rule "reject nested
  components" stays. Composing children into the parent at build time (`wac`) was considered and
  rejected: a composed component's imports are the union of its parts, so the parent's grant
  would reach every child and attenuation would be lost.
- **Under D8** (#112 Q6: the server component asks its host to execute), the whole tree runs
  inside the executor host. So the grant, the offers and the children's bytes travel with the
  execution request as data, and `compose` and `fetch` are served by the executor from a
  content-addressed store the server hands it (verified by CID, so the executor need not trust
  it). Nothing calls back into the server component mid-run, which keeps A's "no
  component-model async".

**What would change it:** a phase-3 page that embeds children chosen at runtime (a feed). That is
the case for B or a bounded form of C, decided with lane A's `jig:ui`.

## Q6. Encrypted channels: what host functions mean on a client

The server never executes content of an encrypted channel (SC-03, D25). So in an encrypted
channel, blocks run only on members' clients, and each member's client runs them independently.

| Option | For | Against |
| --- | --- | --- |
| **A. v0.3: only renderers (and their declared children) run in encrypted channels (recommended)** | Every client runs the same pure function and gets the same output; no host function needs a client-side meaning except `compose` over pinned children; nothing leaves the device | No bots in encrypted channels in v0.3 |
| B. A bot runs on one designated member device, with its own MLS leaf | Bots in encrypted channels | One device is the bot's server: offline means the bot is down; its key and state live on a laptop; multi-device is not designed (lane I) |
| C. A bot runs on the server as an MLS member | Bots work as in open channels | **The operator can read the channel** |

**Recommendation: A, and say plainly in the spec that bots need an open channel in v0.3** (the
same rule D25 already sets for server-run blocks and bridges).

**Where this differs from lane A, for DJ to settle.** #112 Q3 allows C: "a member-operated agent
holding its own MLS leaf may run server-side, as a member", visible in the member list. Visibility
makes it consented rather than hidden, but the agent's leaf keys sit in the operator's process,
so the operator can read the channel from then on, and exit criterion 2 says the operator
cannot read restricted content. Either the criterion gets an explicit carve-out ("unless members
add an operator-hosted agent, which clients mark as such") or C waits. I'd wait: the carve-out
needs a client warning, a distinct marker in the member list, and lane I's device model, none of
which exist in v0.3. If DJ takes the carve-out, this design needs nothing new: the agent is a bot
install whose host is the server, with the same grants and state, and its posts are MLS
application messages its leaf signs.

Client-side meanings in v0.3:

- `compose`: the client resolves declared children from its local store or the server and
  verifies the CID before compiling. Same budgets.
- `blocks` (fetch): not offered to blocks in encrypted channels. A renderer that needs other
  content pins it as a child or a resource.
- Effects: none apply (renderers return no effects).
- Receipts: lane A's in-group comparison (#112 Q3 point 3: the sender puts its `output_hash`
  inside the MLS message, members re-execute and compare) covers the root and its children
  alike, since the children are pinned in the root's manifest. The server's receipt stays
  `sealed`.

B becomes possible once lane I designs multi-device and a bot device can be one of a DID's
devices. It is the likely v0.4 answer.

## Threat register changes (proposed; land with the implementation PRs)

- **AB-04** mitigation: "A block's effective authority is the meet of its manifest request, its
  grant (install or parent offer) and host policy. Import capabilities absent from the grant are
  absent from the linker; scopes are checked on every call; effects are checked before they are
  applied." Status stays Partial until the attenuation tests merge.
- **OP-07** mitigation, add: "Bot state transitions form a hash chain in signed receipts; the
  owning server can withhold or reorder invocations, and a rewrite is detectable, not
  prevented."
- **SC-03**, add: "A server MUST NOT pass a block from an encrypted channel to `fetch` or
  `compose`."
- **New AB-07, bot amplification:** loops between bots, and host work that fuel does not meter
  (compilation, fetches). Mitigation: hop limit on bot-triggered invocations, children declared
  and compiled at install, fetch byte quotas.
- **New SC-04, host-custodied bot keys:** the host can sign as any bot it hosts. Mitigation: the
  install records the host as the key's custodian; a bot's DID is never a person's; a moved bot is
  reinstalled with a new key.

## Where this goes in the spec: JEP-0007

**Recommendation: a new JEP-0007, "Capabilities, block state and nesting,"** rather than a section
of lane A's JEP-0006. JEP-0006 owns the ABI (the `jig:block` worlds, types, receipts' format).
This design adds authority, not ABI: the install block kind, bot DIDs, grants and their
algebra, the state chain, ingest of bot posts, and threat-register entries. They change on
different schedules, and a reviewer of one should not have to approve the other. JEP-0006's own
draft (#112) already lists "host imports, capabilities, state and nesting" as a non-goal handled
by "a companion design", so a separate JEP matches how A scoped theirs. JEP-0007 `requires`
JEP-0006, imports its types and owns `jig:host`. It is drafted after DJ settles the questions
here, so it records decisions rather than options.

## Lane A's Q7: who chooses the code a server executes

**Agreed: operator policy, empty by default** (#112 Q7 option A). It is the "host policy" term in
this design's `request ⊓ grant ⊓ policy`, so the two compose without new machinery:

- **Policy decides whether this server runs the code at all; the grant decides what it may do
  when it runs.** Neither implies the other. A channel owner cannot make a server run a bot the
  operator has not allowed, and an operator's allowlist gives a block no authority in any
  channel.
- **A bot install for a block outside policy is refused** at ingest, with a reason the owner
  can act on. A bot cannot fall back to clients in v0.3 (Q6), so accepting the install would
  promise something nobody runs.
- **A renderer outside policy is `accepted`,** and members' clients execute it, as A proposes.
- **Policy covers the closure.** A parent's CID pins its declared children (Q5), so approving
  a parent by CID approves exactly that tree. Approving by author DID must not approve children
  by other authors: each child is checked on its own, and a tree with one unapproved child is
  refused as a whole.

## Implementation slices (after approval; each one PR, each with its tests)

1. **Vocabulary and grants in `jig-core`.** Typed scopes, `⊑` and `⊓`, the `Capability` change,
   refusal of unknown names and fields. Property tests: meet is commutative, associative and
   idempotent; `a ⊓ b ⊑ a`; no sequence of meets exceeds its first operand.
2. **Linker per grant in `jig-runtime`.** `InstancePre` cache keyed by (code hash, interface
   set); no `wasi:*`. Tests: an ungranted import fails instantiation; a granted one links; a
   component importing `wasi:clocks` is refused.
3. **`block-install` and `timer-fire` kinds, and bot DIDs.** Owner-signed install, host-held key, member-add of the
   bot DID. Tests: a non-owner's install is refused; a grant exceeding the manifest is refused.
4. **`handle` and effects through `ingest`.** Post via ingest with `produced_by`; hop limit.
   Tests: a post outside `effects.post.channels` is refused; a bot loop stops at the limit; a bot
   is not triggered by its own post.
5. **State.** The state table, the fold, the chain in receipts, atomic commit with effects.
   Tests: a failed invocation changes no state; the chain links; over-quota state is refused.
6. **fetch-by-CID.** Scope by grant, verified CID, encrypted channels refused, fetch list in the
   receipt. Tests: out-of-scope CID, encrypted-channel CID and tampered bytes each return
   `not-found` or `not-granted`.
7. **Timer.** One alarm per instance, owner-server only, `timer-fire` blocks through ingest.
   Tests: replace semantics; a missed fire fires once; a fire whose `scheduled_at` disagrees with
   `set_by`, or arrives for a cancelled timer, is flagged by a client.
8. **Nesting.** Declared children, offers, `compose.invoke`, shared fuel and memory, depth limit,
   receipt tree. **The phase-2 exit tests:** a child offered less cannot link what was withheld;
   a child cannot fetch outside the narrowed scope even when its own manifest asks; a child's
   fuel and memory come out of the parent's; exhaustion anywhere aborts the tree; depth 5 is
   refused; an undeclared child is refused; the same tree gives the same output and receipt
   (minus fuel) on two hosts.
9. **Spec:** `block-execution.md` capability section, JEP-0007, threat-register rows. After L1's
   status sweep merges.

Slices 1–2 depend only on lane A's WIT package existing; 3–7 on A's first end-to-end slice; 8 on
both.
