**Author:** DJ + Claude (lane A of the
[v0.2-close / M3-start plan](../plans/2026-10-18-v0.2-close-and-m3-start.md))

**JEP:** [JEP-0006](../../../repos/jig-spec/jep/jep-0006-block-abi.md) (draft, same PR).
**Builds on:** [`ROADMAP.md`](../../ROADMAP.md) phase 2 and its exit criterion, D8, D25 and D28,
and phase 3's UI ABI. Also the
[fuel-portability investigation](../../investigations/2026-08-11-fuel-portability.md) and the

## Goal

The v0.3 exit criterion: *a third party writes, signs and ships a block in under 10 minutes
that runs identically on client and server; a nested block composes with capability
attenuation verified by tests.*

This design covers the part lane A owns:
- the WIT package and worlds a block exports;
- the determinism profile a host enforces;
- what "identical" means and how anyone checks it;
- one execution path for server, client and CLI;
- the receipt format;
- how the package is versioned, including when `jig-server` itself runs as a component (D8).

Lane C owns every host import (`jig:host/*`), capabilities, state and nesting. Lane Dv owns the
developer loop and the registry.

### What "runs identically" means here (DJ's framing)

Blocks can execute anywhere. The requirement is determinism plus verifiability across clients
on different devices and architectures:

- Server-side execution is legitimate where the server can read the content: open channels,
  and blocks the server itself owns (bots, bridges, indexers).
- The server cannot execute encrypted content (SC-03), so blocks in encrypted channels run on
  members' devices. A member-operated agent holding its own MLS leaf may run server-side, as a
  member.
- If D25's follow-up makes every channel encrypted by default, server-side execution shrinks to
  server-owned blocks plus agents that are members. The section on Q3 says what that does to
  verification.

### wasmtime 49 facts this design relies on

Checked against the wasmtime 49.0.3 source and small experiments. Sources are in the appendix.

- **The component model and component-model async are both on by default.** A strictly
  synchronous engine needs `Config::concurrency_support(false)`.
- **WASM 3.0 is on by default:** GC, memory64, exceptions, multi-memory, tail calls and wide
  arithmetic. jig's engine turns off only threads, SIMD and relaxed SIMD. Today the validator
  covers the gap. The engine should match it (passed to L2).
- **`Component::new` validates every nested core module** against the engine's feature set, so
  a feature the engine disables is refused at compile time.
- **Fuel accounting changed within 49.x patch releases** (49.0.0 and 49.0.1). A fuel number
  is comparable only at the same patch version.
- **Canonical ABI NaNs.** Lifting canonicalizes NaNs, but wasmtime passes float bits through
  unchanged. Keeping floats out of the WIT removes the question.
- **Resource handle tables are deterministic.** Freed slots are reused last-in, first-out.
- **`wasm32-wasip2` is the wrong guest target.** A pure Rust `wasm32-wasip2` component imports
  14 WASI interfaces (std's panic and print machinery).
  - `wasm32-unknown-unknown` plus `wit-component`'s `ComponentEncoder` gives zero imports and one
    core module, and passes the WASM 2.0 minus SIMD validation.
  - `wasm32v1-none` (tier 2, core+alloc) is a candidate; it is untested with wit-bindgen.
- **Pulley versus native.** On x86_64, the interpreter and native code gave identical fuel,
  results and out-of-fuel traps.
  - With canonicalization, NaN bits match between x86_64 and aarch64; without it, x86_64
    produces `0xffc00000`.
  - wasmtime with Pulley links for `wasm32-unknown-unknown` as `no_std`. It has not been run
    there, and it is not an officially supported path.
- **jco (component to JS plus core Wasm, for browsers)** does not canonicalize NaNs, and its
  `realloc` call order may differ from wasmtime's.
- **The wasmtime linker** holds several incompatible package versions side by side and matches
  semver-compatible ones in both directions. At `0.x`, every minor bump is breaking.

## The six questions

Each question has options, a recommendation and its trade-offs. DJ decides; the
recommendations are where this design leans.

### Q1. WIT worlds and exports

How do effectful blocks stay verifiable? The answer fixes the world shape, which lane C needs.

- **A. Effects are returned as data.** `handle(invocation) -> list<effect>`.
  - The host checks each effect against the block's granted capabilities, then applies it.
  - Reads done mid-call (state, fetch-block-by-CID) are imports addressed by content (lane C).
    Their answers are a deterministic function of recorded inputs.
  - Anyone holding the inputs can re-run the call and must get the same effects.
- **B. Effects are host functions the block calls mid-run.** This is what `block-execution.md`
  describes (`net.fetch`, `crypto.sign`).
  - Easier to write ("fetch, then decide").
  - Results can only be *attested*, never re-derived.
  - Every import needs a cost entry, or the block can push work to the host without paying for
    it (fuel-portability, "an import is a fuel-accounting hole").
- **C. Pure renderers only in v0.3.**
  - Smallest scope.
  - Cannot meet the exit criterion (nesting with attenuation), and leaves C nothing to design
    against.

**Recommendation: A.** Keep B only for effects that cannot be re-run (`net.fetch`, inference),
as a later tier verified by attestation, which the fuel-portability doc already sketches.

Consequences:
- `net.fetch` and the weather-block example leave v0.3.
- A multi-step workflow becomes several invocations. Each one is re-executable, with state
  between them held by the host and addressed by CID (C).

Proposed package (sketch, not approved; C extends `effect` and owns all imports):

```wit
package jig:block@0.1.0;

interface types {
  // No f32/f64 anywhere in the ABI.
  record payload { media-type: string, body: list<u8> }

  // Every piece of context is input data: time, sender, channel, and later seeds.
  // ("Invert side data into explicit input", fuel-portability.)
  // `hlc-*` is the owning server's signed ingest HLC (form pending L7). It is never the
  // author's `hlc_ts` (TM-02). See "Answers to lane C".
  record invocation {
    block-cid: string,
    sender-did: string,
    channel: string,
    hlc-wall-ms: u64,
    hlc-logical: u32,
    input: payload,
  }

  // Deterministic guest-reported failures: these are comparable outcomes.
  variant block-error { invalid-input(string), failed(string) }
}

interface render {
  use types.{invocation, payload, block-error};
  render: func(inv: invocation) -> result<payload, block-error>;
}

interface handler {
  use types.{invocation, payload, block-error};
  variant effect { post(payload) /* C: timer, ... */ }
  // State is a return value, not an effect: it commits atomically with the effects,
  // and `none` means unchanged.
  record handled { effects: list<effect>, state: option<list<u8>> }
  handle: func(inv: invocation, state: list<u8>) -> result<handled, block-error>;
}

// Tier 1: anyone can verify it by re-executing it. Its only possible import is lane C's
// `jig:host/compose`, for children the manifest pins by CID, which are themselves renderers.
world renderer { export render; }

// Tier 2: capability-bearing. C adds `import jig:host/...` lines.
world bot { export handler; }
```

**Phase 3 hook.** The UI ABI goes in a separate package, `jig:ui`, with `world viewer { export
view; }` returning a declarative view tree. It is separate so the UI can iterate without bumping
`jig:block`. One component may implement both `renderer` and `viewer`. Nothing in `jig:block`
reserves UI types now.

**One function, or a named export per role?** The alternative to the above is a single generic
`run(invocation) -> result<payload, block-error>` with the role in the manifest. Typed exports
are recommended:
- the host can check a component's world statically at upload, rather than finding out at call
  time;
- the role (render or handle) decides whether effects are allowed at all, and that belongs in
  the type.

### Q2. Determinism for components

What may a component use, and how does the validator handle it?

- **A. No WASI; jig-only imports.** Blocks import at most `jig:host/compose` (renderer) or only `jig:host/*`
  interfaces that a manifest capability grants (bot).
- **B. A deterministic WASI 0.2 subset**, for example stdout for logging and a fixed
  environment.
  - It makes `wasm32-wasip2` builds work out of the box.
  - No standard deterministic WASI profile exists. The fuel-portability matrix showed a WASI
    p1 module running different instruction counts per host OS through `_start`'s environment
    walk. A pure `wasip2` build drags in 14 interfaces anyway.
- **C. Full WASI, virtualized** (WASI-Virt style).
  - Most compatible.
  - Every virtualized answer becomes protocol surface that a second implementation must
    reproduce bit for bit. Its maintenance status is unverified.

**Recommendation: A.** The guest target is `wasm32-unknown-unknown` (or `wasm32v1-none`) plus
`ComponentEncoder`; `jig block new` templates hide that (Dv).

The **jig deterministic profile, version 1**, which hosts enforce at upload and again at
compile:

1. **Component level.** Validate with `(WASM2 | COMPONENT_MODEL) & !SIMD`.
   - Reject component-model async, threading, `error-context` and every other gated component
     feature.
   - Reject nested components until nesting (C) needs them.
2. **Each core module** must pass today's `DETERMINISTIC_FEATURES` and the float ban. Each
   memory and table must declare a maximum, and that maximum must not exceed the manifest's
   limit.
3. **Imports.** A component's imports must be a subset of the `jig:host/*` interfaces its
   manifest capabilities grant, matched by name and semver-compatible version. `renderer` may
   import only `jig:host/compose`. Any `wasi:*` import is refused.
4. **Exports.** The component must export exactly the interface its declared world names.
5. **Engine.** Set the engine's features to the profile explicitly rather than switching
   defaults off one at a time. That means `concurrency_support(false)`, NaN canonicalization
   on (defence in depth: floats are banned anyway), fuel on, and epoch on as liveness only.
6. **Floats stay banned in v0.3.** jco cannot canonicalize NaNs, and this keeps the browser
   path open. Phase 3 layout may want floats; revisit then with a profile version 2.

**Two non-portable trap sources.** Fuel exhaustion (fuel is not portable across engine
versions) and **stack exhaustion** (native stack use differs by architecture, by Cranelift
version and between Pulley and native) can happen on one conforming host and not another. Both
make the outcome *incomplete*, which asserts nothing (Q3). Memory growth beyond the manifest
limit is deterministic, since the limit comes from the manifest, so it is an ordinary trap.

### Q3. What "identical" means and how it is checked

**Definition (recommended).** A *run* is identified by:
- the component's CID;
- the world and its version;
- the invocation hash, `blake3` over the canonical encoding of the `invocation` value;
- for `bot`, the hash of `state` before the call and the content-addressed answers to its
  fetch imports;
- for a composed block, the CIDs of the children its manifest pins (covered by the manifest's
  CID).

A run has one of three outcomes:

| Outcome | Meaning | Comparable? |
| --- | --- | --- |
| `ok(output_hash)` | The export returned `ok`. | Yes |
| `error(error_hash)` | The export returned `err(block-error)`, or the guest trapped deterministically (`unreachable`, an out-of-bounds access, memory past the manifest limit). | Yes |
| `incomplete(reason)` | Fuel, stack or epoch exhaustion, a host fault, or a capability refusal by host policy. | **No:** it asserts nothing about the block |

- **The equality.** Two conforming executors that both reach a comparable outcome for the same
  run MUST reach the same one, whatever the architecture, operating system, engine or engine
  version. Engine identity is recorded for diagnosis and for labelling fuel. It is never part
  of the equality.
- **`output_hash`** is `blake3` over the canonical encoding of the returned WIT value.
  - The JEP fixes one encoding of WIT values, deterministic CBOR (RFC 8949 §4.2) under a fixed
    mapping, so `renderer` and `bot` share one rule.
  - For `payload` that is media type plus bytes, so no guest-language serializer is involved.
- **Hashing on the host side is safe here.** The fuel-portability rule ("compute it inside the
  sandbox") exists because *measurements* are host-dependent. The lifted return value is not a
  measurement: lifting is deterministic once floats are excluded, so hashing it on the host is a
  pure function of the guest's output. Unlike today's `render_hash`, it also covers the whole
  output.
- **Fuel is never compared** (fuel-portability, recommendation 1).

**How it is checked:**

1. **Conformance vectors** in the repo: component, invocation, expected outcome. CI runs them
   on x86_64 and aarch64 Linux (`fuel-portability.yml` already runs both architectures), plus
   wasmtime with Pulley. macOS runs on dispatch.
   - A browser executor (jco or Pulley-in-wasm) counts as conforming only once it passes the
     same vectors.
   - That makes the cross-architecture test the first slice's exit gate.
2. **Open channels.** The server executes and signs a receipt carrying `output_hash`.
   - Clients that render re-execute (they must run the block to display it anyway) and compare.
   - A mismatch on a comparable outcome is evidence against the server or against a client
     executor (OP-07). It is surfaced, never silently resolved.
3. **Encrypted channels.** The server MUST NOT execute (SC-03).
   - The sender executes and puts its `output_hash` *inside* the encrypted application message.
   - Every member re-executes on receipt and compares.
   - The server's receipt stays `sealed`, with no content-derived value (PV-02).
   - Verification therefore moves inside the group, and the operator learns nothing.
4. **Server-owned blocks** (bots, bridges, indexers) execute on the server, as the server.
   - **In v0.3, not in encrypted channels.** This design concedes lane C's objection (C's DJ
     question 8). See "Server-run agents in encrypted channels" below.

**What all-encrypted-by-default (D25 follow-up) costs.**
- The server stops being an executor for channel content, and server-side render parity
  (OP-07 as written) disappears for those channels.
- Verification still works through point 3.
- Server-side automation in encrypted channels is unavailable in v0.3 (see below). Members'
  own devices can still run bots.

So the block ABI does not block D25's follow-up. It changes OP-07's mitigation from "clients
compare servers" to "members compare each other".

### Q4. One ABI for server, client and CLI; deletion plan

**Recommendation: one component path in `jig-runtime`, used everywhere.**

- **Server.** `jig-pipeline`'s executor runs components through the profile above.
- **Client.** `jig-client` embeds `jig-runtime` (roadmap phase 2), behind a cargo feature so
  a thin client can opt out. A client without it shows a block's fallback text, and says it
  could not verify the block.
- **CLI.** `jig block run` executes components only, if it survives L3's proposal to remove
  `block` until Dv rebuilds it.

**Deletion plan** (each step its own PR, with no behaviour change mixed in):

1. **ABI 2** (`Runtime::execute`, the WASI p1 linker, `wasi_preview1_deterministic`, the
   v0.2 `BlockReceipt`).
   - It goes as soon as D28 has removed `POST /blocks` and `jig block run` is gone or moved to
     components.
   - `wasmtime-wasi` leaves the server's dependency tree, and the `wasm32-wasip1` toolchain
     target goes with it (coordinate with L5 on `release.yml`).
2. **ABI 1.**
   - Port `text-block` to `world renderer`, as a component built from `wasm32-unknown-unknown`.
   - The server's `text-render` kind switches to it.
   - Then delete `payload.rs` and the `jig_alloc`/`jig_dealloc` exports.
3. **Compatibility.**
   - The port does not change `text-render`'s `render_hash`, which is still
     `blake3(canonical_text)` computed by the same Rust code. Mixed-version servers keep
     agreeing during a rollout.
   - Generic blocks use `output_hash`.
   - `text-render` may move to `output_hash` later, as an explicit kind version bump: it would
     break parity with servers that have not upgraded.
4. **Features.** Delete the jig-runtime `component-model`, `deterministic` and
   `receipt-signing` cargo features, or wire them up. L2 is already sweeping these. The
   component path should not hide behind a feature, because every executor needs it.

### Q5. Receipt format

**Recommendation: one format with three kinds, replacing all four.**

```json
{
  "v": "0.3",
  "kind": "exec",
  "block_cid": "…",
  "executor": "did:jig:…",
  "role": "server",
  "component": "blake3:…",
  "world": "jig:block/renderer@0.1.0",
  "invocation_hash": "blake3:…",
  "outcome": { "status": "ok", "hash": "blake3:…", "len": 512 },
  "engine": {
    "name": "wasmtime",
    "version": "49.0.3",
    "profile": "jig-det-1",
    "pricing_schedule": "…",
    "fuel_used": 18098
  },
  "produced_at": 1760000000
}
```

- **`kind`.**
  - `exec`: something ran.
  - `sealed`: encrypted content; nothing ran and no content-derived field is present (PV-02).
  - `accepted`: persisted, no executable content. This replaces `0.2-synthetic`.
- **`role`.** `server`, or `member` for a member-signed claim inside an encrypted group.
- **`outcome.status`.** `ok` or `error` (both carry a `hash`), or `incomplete` (carries a
  `reason`, never a hash).
  - The old `soft_fail`/`hard_fail` and billing affordances leave the v0.3 receipt.
  - Pricing comes back with the attested tier.
- **`engine`** is labelled telemetry, as the fuel-portability doc recommends.
  - `version` is the exact wasmtime patch version.
  - `pricing_schedule` is the enforced version L2 is building.
  - `fuel_used` is wasm fuel only. There is no `fuel_total` summed across host-attributed
    buckets (the defect the investigation names). Host meters, when C adds them, sit beside
    it, labelled, and are never summed into it.
- **`applied`** (from lane C; agreed): which of the returned effects the host applied or
  refused, and why.
  - It sits outside `outcome`. The outcome hash covers what the block *returned*; `applied` is
    the host's policy claim.
  - Hosts with different grants therefore still agree on the run, and differ only in
    `applied`.
- **`host` meters for each node of the `children` tree** (lane C; agreed; C's DJ question 9).
  - Named host counters (bytes, calls) sit beside `engine.fuel_used` and are never summed into
    it or into a `fuel_total`.
  - Folding host costs into fuel would let a wasmtime patch release change what a grant
    allows, and would repeat the summing defect the fuel-portability investigation names.
- **Signing.** Keep today's wrapper (`canonical_hex` plus `sig_hex`). The signature covers
  exact bytes, so the payload needs no canonicalization; verifiers hash what was signed.
- **Docs.** `receipts.md` is rewritten to this format in the implementation PR (after L1's
  banners), and drops fuel-comparison replay.

### Q6. Constraints from D8, and versioning

**D8: the server as a component.** A `jig-server` compiled to a WASI 0.2 component cannot JIT,
so it cannot run wasmtime with Cranelift inside itself. Options:

- **A. Its host executes blocks.** The server component imports an executor interface
  (`jig:runtime/executor`, owned by lane A, distinct from C's block-facing `jig:host/*`) and
  hands the host component bytes plus an invocation.
- **B. Pulley inside the server component.** It links, but nobody has run it, wasmtime does
  not support it, and it is slow.

**Recommendation: A**, with B as a fallback experiment. What this constrains *now*:
- the block ABI must not assume wasmtime runs in the same process;
- nothing may need threads, fibers or component-model async;
- the receipt's `engine` names whoever actually executed.

Phase 4 owns the server component's world.

**Versioning.**
- The package is `jig:block@0.1.0` during v0.3 development. Every minor version is breaking
  while at `0.x`.
- A manifest names its world with the full version (`jig:block/renderer@0.1.0`).
- A host MUST link every version it advertises, and advertises them in the handshake
  capabilities (JEP-0002), so a client knows before rendering whether it can verify a block.
- Go to `1.0.0` at the v0.3 exit. After that, additions are minor versions gated with
  `@since`, and incompatible changes are a new major linked alongside the old one.
- The profile is versioned separately (`jig-det-1`) because it can tighten without changing
  any WIT.

## A seventh question this design surfaces

### Q7. Who chooses the code a server executes?

Today `text-render` is safe because *the server picks the module*. If the sender picked it, they
would choose the code that computes their own hash (`executor.rs`'s header comment). SC-03
says "a host executes only modules it chose". D28 removes `POST /blocks` because it executes
sender code without a signature check. The v0.3 exit criterion needs third-party blocks to run
on servers.

- **A. Operator policy.** A server executes a component only if its CID, or its signing
  author, is on the operator's policy (an allowlist, or later a reputation rule). Otherwise it
  persists the block with an `accepted` receipt and leaves execution to clients. SC-03's "a
  host executes only modules it chose" then holds through policy.
- **B. Any signed component.** Rely on the profile and the sandbox alone. This weakens SC-03
  to "a host executes only signed, validated modules".
- **C. Clients only.** The server never executes third-party code.
  - The safest for the server, and it fits D25's direction.
  - But "runs on server" in the exit criterion would then be met only by server-owned blocks.

**Recommendation: A.** The default policy is empty: the server executes only its own blocks,
the same as today. Operators opt in.

Verification does not depend on who chose the code, because any party with the component can
re-execute. Who chose it matters only for the host's own exposure. The manifest field that
names a block's component and world is Dv's and C's to shape; this design needs only the
component CID and the world name.

## Answers to lane C (draft #117, "Questions for lane A")

These follow the recommendations above and are equally unapproved.

1. **Guest target.** `wasm32-unknown-unknown` (or `wasm32v1-none`) plus `wit-bindgen`, wrapped
   by `ComponentEncoder`. No virtual WASI: see Q2. Dv's templates hide the build steps.
2. **Children in `renderer`.** Yes. A renderer may import `jig:host/compose`, on these
   conditions:
   - its children are pinned by CID in the manifest;
   - each child is itself a `renderer` (no effects reachable from a render);
   - an `incomplete` outcome in any child makes the whole tree `incomplete`;
   - the depth limit applies.

   Run identity then covers the closure through the manifest's CID, so verification by
   re-execution holds. A client must be able to fetch every child component before it can
   verify the tree.
3. **`handle` signature.** Accepted:
   `handle(inv: invocation, state: list<u8>) -> result<handled, block-error>`, with
   `handled = { effects: list<effect>, state: option<list<u8>> }`. State is a return field
   rather than an effect, because it must commit atomically with the effects and it is not an
   externally visible action. `none` means unchanged. The hash of the state passed in is part of
   the run's identity.
4. **`invocation.hlc`.** Agreed that it is never the trigger's author-set `hlc_ts`. One
   refinement: it is the **owning server's signed ingest HLC for the triggering block**, not "the
   executor's clock at invocation".
   - This design assumes only that a server-signed ingest HLC exists. Its field name, and whether
     it is signed per block or through batched signed heads, wait on DJ's answers to L7's
     questions.
   - Renderers run on every client, and every executor must see the same value, or re-execution
     diverges.
   - For a bot running on the owning server, the two coincide.
5. **Receipt fields.** The same v0.3 format (Q5), kind `exec` with `world` set to the `bot`
   world. It carries these optional fields: `instance`, `state_before`, `state_after`,
   `fetches`, `effects_digest` and `children` (a tree of child receipts, each with its own
   `component`, `invocation_hash` and `outcome`). `invocation` is the existing
   `invocation_hash`. There is no separate `0.3-invoke` format.
6. **Pool sizing and resource limits.** See below.
7. **Fetches that return `not-found` count toward the run's identity** (C's follow-up). Agreed.
   - The run's fetch list records each CID with its answer: found (the bytes are verified
     against the CID), `not-found` or `not-granted`.
   - A re-executor replays the recorded answers instead of fetching afresh; it does not get a
     different run just because the CID has since become available.
   - `not-granted` follows from the grant, so it is deterministic.
   - A recorded `not-found` is the executor's claim and can be checked: anyone holding the CID
     at that time can contest a receipt that suppressed it.

### Server-run agents in encrypted channels (C's DJ question 8)

DJ's framing (top of this doc) and an earlier draft of this design allowed a bot operated by the server to run in an encrypted
channel as a member, with its own MLS leaf. C objects: the operator would then hold keys that
read the channel, against exit criterion 2 ("the operator cannot read restricted content").

**The counter-argument, for DJ to weigh.** The threat behind criterion 2 is the operator reading
*covertly*, or by default. An agent differs from that in three ways:
- it is added by the channel's owner through an ordinary member-add;
- it is listed as a member;
- it is labelled with the server operating it.

A member's laptop could equally be run by someone the members distrust. On this view, a
consented, visible agent is a member, not an operator capability.

**Why I concede for v0.3.**
- Users will not reliably read "this bot is operated by server X" as "server X can read this
  channel".
- A server that offers bots by default turns consent into a single click, which wears the
  criterion down in practice.
- Nothing in v0.3's exit criterion needs it: bots in open channels plus members' own devices
  are enough.

The ABI does not preclude the agent model. If DJ later allows it, it needs:
- an agent DID distinct from the server's;
- addition by the owner only;
- a persistent label in every client.

Recommendation: no server-run agents in encrypted channels in v0.3, and revisit with D25's
follow-up.

### Resource limits under nesting

- **Instances.** A component with N core modules uses N core instance slots of wasmtime's
  pooling allocator, and a nested tree uses the sum over its closure.
- **Deadlock.** The executor's `Slots` gate counts one permit per call today. With nesting, a
  parent holding a permit while it waits for a child's permit can deadlock the pool under load.
- **Recommendation.** At admission, compute each tree's worst-case slot count from its manifest
  closure, which is known before execution because children are pinned. Reserve that many
  permits atomically, all or nothing. Refuse a tree whose count exceeds the pool at upload,
  not at run time.
- **Shared budgets.** Fuel and memory are one budget for the whole tree (C's design).
  Exhaustion anywhere makes the whole tree `incomplete`.
- **Depth.** A depth limit (C proposes refusing depth 5) bounds the closure size.

## First slice (planned after approval)

One component running end to end on server and client, with a cross-architecture determinism
test:

1. A WIT package in `repos/jig-spec/wit/`. A `text-block` component built from
   `wasm32-unknown-unknown` plus `ComponentEncoder`, with a reproducible build check.
2. The component path in `jig-runtime`: profile validator, engine profile, `renderer`
   bindings.
3. The server's `text-render` kind executes the component. The receipt moves to the v0.3 `exec`
   kind.
4. `jig-client` executes the same artifact for an open channel and compares `output_hash` with
   the server's receipt.

The implementation plan, with one PR per step, follows DJ's approval.

## Risks and unknowns

- **Stack exhaustion** is the least obvious non-portable trap. If real blocks hit it often,
  `incomplete` becomes common. A conservative guest stack size in the templates mitigates it.
- **`wasm32v1-none` with wit-bindgen** is untested. `wasm32-unknown-unknown` works today.
- **Browser execution** (jco or Pulley-in-wasm) is unproven. It must pass the vectors before it
  counts as a conforming client.
- **Canonical encoding of WIT values** is new protocol surface. Keep it small: the v0.3 types
  are records, variants, lists, strings and integers.
