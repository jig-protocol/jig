# v0.3 block developer loop and registry: plan

**Date:** 2026-10-18
**Design:** [`2026-10-18-v0.3-block-dev-loop-design.md`](../specs/2026-10-18-v0.3-block-dev-loop-design.md)
(decisions Dv1–Dv6). The protocol objects go in JEP-0011.
**Status:** Plan, not started.

## Goal and exit gate

The first half of the phase-2 exit criterion: a third party writes, signs and ships a block in
under 10 minutes, and it runs identically on client and server.

The work is done when all of these hold:

1. `block-dev-smoke.yml` passes on `main`, nightly, within its 5-minute machine budget, on Linux
   and macOS. The run goes from template to build, sign, publish, server `exec` receipt, and
   client re-execution that agrees with the receipt.
2. A person who has not seen the loop follows the author's guide and records the time in the
   release notes.
3. Programs, channel policies and the read-gate rule are specified in JEP-0011, and each MUST in
   it has a test.

Out of scope here: bots, effects and nesting themselves (lane C); the ABI, receipts and vectors
(lane A); names and cross-server fetch (lane F); deny lists and reports (lane R).

## Slices (one PR each, with its tests)

### 1. `jig block new`, `build`, `lint` (renderer template)

- The `renderer` template:
  - `.cargo/config.toml` targets `wasm32-unknown-unknown` with a declared memory maximum and a
    conservative stack size;
  - the release profile uses `opt-level = "s"`, LTO, `strip` and `panic = "abort"`;
  - `wit-bindgen` is pinned exactly;
  - `jig-block.toml` and two vectors are included.
- `new` writes the `jig:block` WIT from the `jig` binary itself.
- `build` runs cargo, then componentizes in-process with `wit-component` (no `wasm-tools`), then
  runs `lint`.
- `lint` calls jig-core's `jig-det-1` validator. For author mistakes it gives readable errors: a
  float instruction is reported with the function it is in, plus a missing memory maximum, a
  `wasi:*` import and a wrong world.
- Tests:
  - the template builds and passes `lint`;
  - each hazard is reproduced in a fixture and gets its message.
- Measure the size `wit-component` adds to the `jig` binary, and put it in the PR.
- Needs: #127, A's WIT and validator.

### 2. `jig block run`, `test`

- `run` synthesizes an invocation and prints the outcome class, hash and output.
- `test` runs the vectors, and `--bless` records new expected values.
- Both call A's single component path with A's explicit engine profile.
- Tests:
  - `ok`, `error` and `incomplete` are each classified correctly;
  - `incomplete` carries no hash.
- Needs: A steps 2 and 4.

### 3. JEP-0011: program objects and channel policy

The JEP covers:
- the program manifest (fields, dcbor payload, COSE_Sign1, and a CID over the unsigned manifest
  plus the component);
- the `block-program`, `render`, `channel-policy`, `host-approval`, `host-withdrawal` and `program-yank` kinds;
- the read-gate rule (linking under the sender's authority, plus the invariant that a CID is never
  served to a caller who cannot read a channel holding it);
- the server's restriction list;
- client execution: the channel policy decides, the user can still refuse, per-user allows exist,
  allows by DID lapse at rotation, and allowing a parent allows its whole tree.

This is a spec-only PR, drafted from the design's decisions. The threat-register rows it proposes
(SC-01, SC-02, AB-07, and a new PV row for the policy allow list) land with the slices that
implement them.

### 4. Program manifest: `sign`, `verify`

- The manifest type in jig-core, encoded with `dcbor` and signed with `cose::sign1`. The program
  CID is computed with `bundle.rs`'s derivation.
- `sign` writes a `.jigprog` file, and `verify` runs the same checks as ingest (slice 5), through
  one function in jig-core.
- Tests:
  - golden CIDs;
  - signing the same input twice gives the same CID;
  - a tampered component, a tampered manifest, a wrong author and a missing child each fail
    `verify`.
- Needs: #175, slice 3.

### 5. Server: `block-program` ingest and the read gate; `publish`

- Ingest validates a program with slice 4's verifier, stores it by CID, issues an `accepted`
  receipt, and never executes it.
- A program-to-channel holdings table.
- `GET /api/v1/blocks/{cid}` serves a CID only to callers who can read a channel that holds it.
- A message naming program P links P into its channel only if the sender can read a channel
  already holding P, or attaches P's bytes. Otherwise ingest refuses it with
  `program-unavailable`.
- `jig block publish` defaults to the author's open feed channel.
- Tests:
  - publishing the same program twice is a no-op;
  - a caller outside every holding channel cannot fetch the program;
  - a sender who knows P's CID but can read no channel holding it cannot link P;
  - attaching the bytes links P.
- Needs: slice 4, A step 6 (receipts).

### 6. Server: `render` execution under operator policy

- A `render` message names a program and its input.
- The server executes it only if the program is in operator policy (A7) and issues an `exec`
  receipt carrying both `component` and `program`. Otherwise it issues `accepted`.
- Operator policy is keyed by program CID or author DID. Allowing an author never extends to
  children by other authors.
- Tests:
  - a program inside policy gets `exec`, one outside gets `accepted`;
  - the closure rule;
  - encrypted channels never execute.
- Needs: slice 5, A step 6.

### 7. Channel policy: server side

- Operators publish a restriction list, identified by CID.
- `channel-policy` is owner-signed (COSE_Sign1) and chained by `seq`/`prev`.
- The home server issues `host-approval` and `host-withdrawal` (COSE_Sign1) for policies and for
  `block-install`. They are ordered by the ingest chain (JEP-0011 §5.3).
- The server refuses to approve a policy that its restrictions forbid.
- When its restrictions change, the server re-checks every policy it approved. It re-approves those that still pass and issues
  `host-withdrawal` for the rest.
- The policy is a plaintext control block, including in encrypted channels.
- Tests:
  - only the owner can propose a policy;
  - a forbidden policy is refused;
  - a change to the restrictions causes a withdrawal;
  - the amendment chain links;
  - in an encrypted channel the policy is readable but the messages stay encrypted.
- The sequencer-move approval (F's `contract-accept`) waits for F's build, and the doc says so.
- Needs: slice 3, #175.

### 8. Client: execution policy and comparison

- `jig-client` auto-runs only renderers allowed by an effective policy: an owner-signed, unbroken chain whose
  current ingest entry is a `host-approval` from the current home server.
  Everything else is click-to-run.
- Before running, it warns about any conflict between the policy and the user's own restrictions.
- Per-user allows ("always run this program", "always run this author") and a per-user deny list,
  stored locally.
- Allows by DID lapse at rotation until confirmed (JEP-0004's AliasLink).
- Allowing a parent allows its whole tree, and a tree is never partly rendered.
- A compile cap on distinct uncached programs per channel per minute.
- `jig block run --replay` re-executes a real message and compares it with the server's receipt
  (A step 7). In-group comparison covers only the members who executed.
- Tests:
  - a policy without the owner's signature, or whose current entry is a withdrawal or an approval
    from a former home server, is ignored;
  - a withdrawn policy falls back to click-to-run;
  - a deny entry beats a channel allow;
  - a rotated DID lapses;
  - a tree with one disallowed child is click-to-run;
  - hitting the cap gives fallback text.
- Needs: slices 6 and 7, A step 7.

### 9. The KPI: `block-dev-smoke.yml` and its script

- `scripts/block-dev-smoke.sh <budget-seconds>` runs these steps on a runner with no Rust cache:
  1. install `jig`;
  2. install the Rust toolchain;
  3. `jig init` and `new`, plus a scripted edit;
  4. `build`, `test` and `sign`;
  5. create a channel, which sets its policy;
  6. `publish` the program and amend the policy to allow it;
  7. post a `render` message, receive the server's `exec` receipt, and run `--replay`, which must
     agree.

  The script prints a time for each step.
- The workflow:
  - runs on non-draft PRs whose changes match a path filter;
  - runs nightly on `main` on Linux and macOS;
  - is not required, and is not in the merge queue;
  - leaves `ci.yml` unchanged.
- L5 adds a `workflow_call` from `release.yml` that runs it against the published install.
- Needs: slices 1–8.

### 10. `bot` template

- A counter bot: state, a `post` effect, and tight requested scopes. The guide shows the owner's
  `block-install`, which the server approves with a `host-approval`.
- Needs: C slices 3–5.

### 11. `composed` template

- A renderer that pins one child, offers it nothing, and branches on the child's `failed`.
- Needs: C slice 8.

### 12. The author's guide

- Written against slice 9's script, so the two describe the same steps.
- Pages for the walkthrough, each template, and every `lint` error with its cause.
- The location is L1's choice; the proposal is `docs/guides/block-authoring.md`.
- Needs: slice 9.

- 1 → 2 can start as soon as #127 and A's steps 1–4 land. They need no server work.
- 3 is spec only and can start now.
- 4 needs 3 and #175.
- 5 → 6 follow 4.

- 10 and 11 follow C's slices.
- 12 comes last.

## Risks

- **`wit-bindgen` drift.** The nightly run catches it, and the template's exact pin protects
  authors in the meantime.
- **Cold build time on CI runners.** It is unmeasured. Fix the budget only after slice 9's first
  runs.
- **Policy leak in encrypted channels.** Countersigned policies reveal a channel's allow list to
  its server. This is accepted for v0.3, gets a PV row, and should be revisited if it proves
  sensitive.
- **Withdrawal churn.** An operator who changes restrictions often forces owners to amend often.
  The withdrawal names the conflicting entry so the owner can fix it in one step.
